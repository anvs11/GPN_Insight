# Слой хранения SQLite v2

Это результат этапа участника 3: постоянные источники и их версии, метаданные материалов, нормализация, потребности, темы/связи, review, решения, ручные события, запуски и журнал завершённых регистраций. Загрузка файлов, маскирование, модели, группировка и выполнение pipeline здесь не реализуются.

## Что было и что добавлено

Основа уже сохраняла синтетическую карточку, источники, связи и решения «Исследуется» с проверкой version. Теперь `Repository` использует версии источников и новые таблицы вместо перезаписи исходной записи. Публичные методы демо/API сохранены; существующие источники, topic_id, решения, события и отметки seed переносятся без изменения содержимого. HTTP-срез остаётся прежним: новых ручек импорта/run/review не добавлено.

`backend/app/db.py` управляет соединениями и инициализацией; `migrations.py` — переносом v1→v2; `storage.py` — регистрацией/источниками/нормализацией/review/run; `repositories.py` — темами, связями, решениями и ручными изменениями. Публичный импорт остаётся `from app.repositories import Repository, RepositoryError`.

## Безопасный init-db

Перед первым запуском новой версии остановите старый сервер: приложение пилота работает в одном процессе. Из `backend/`:

```powershell
..\.venv\Scripts\python.exe -X utf8 -m app.cli init-db
..\.venv\Scripts\python.exe -X utf8 -m app.cli init-db
```

Первый вызов для базы v1 создаёт согласованную копию через SQLite backup в соседнем `backups/<имя>.v1.<uuid>.db`, затем одной транзакцией создаёт v2 и переносит записи. Повтор на v2 не создаёт новую копию и не меняет данные. Неизвестная версия или непустая база без версии отклоняется. Сбой переноса откатывает также DDL: версия и старые записи остаются v1. CLI сообщает фактическую версию и создание копии. Обычный старт FastAPI вызывает тот же initialize; init-db не сбрасывает базу и не прерывает работающие run.

Таблицы v1 `sources`, `needs`, `topic_needs` остаются историческим снимком и больше не используются для новых записей. `topics`, `decision_events`, `demo_fixtures` сохраняются. Новые таблицы: `source_records`, `source_versions`, `registered_materials`, `source_materials`, `normalized_documents`, `normalized_fragments`, `normalization_history`, `stored_needs`, `topic_need_links`, `catalog_state`, `review_records`, `review_needs`, `review_history`, `manual_overrides`, `topic_changes`, `run_records`, `import_log`. Не пишите в них напрямую из других компонентов: используйте репозиторий, который обеспечивает проверки и транзакцию.

## Граница с участником 1

Участник 1 принимает manifest/файлы, проверяет содержимое, имена, сигнатуры, лимиты и разрешённые пути, перемещает подготовленные файлы под серверными именами в uploads. Затем он передаёт `DatasetRegistration` в `Repository.register_dataset`. Внутри регистрации нет чтения, проверки существования, перемещения или удаления файлов и нет вызовов моделей. `RegisteredMaterial.storage_path` — относительный серверный путь от APP_UPLOAD_ROOT, а не путь клиента. Источник manifest связывается с материалом через asset_id, original_filename и MIME/kind.

Минимальный вызов после подготовки файлов:

```python
from app.config import Settings
from app.repositories import Repository
from app.schemas import DatasetRegistration

settings = Settings()
repo = Repository(settings.repo_path(settings.app_db_path))
batch = DatasetRegistration(
    dataset_id="permitted-export",
    product_id="webneft",
    synthetic=True,
    origin="imported",
    tickets=validated_tickets,
    materials=prepared_materials,
)
result = repo.register_dataset(batch, registration_id=server_request_uuid)
# Только после возврата result одиночная транзакция уже зафиксирована.
```

`origin=authored` применяется к вручную подготовленным данным, `imported` — к зарегистрированной выгрузке; synthetic указывается явно. Происхождение уже известного источника не меняется молча. Один набор относится к одному продукту. Схемы теперь допускают идентификатор продукта, а не только literal webneft, чтобы уникальность пары product_id/source_id была настоящим ограничением БД; HTTP-пилот по-прежнему относится к «Вебнефти».

`register_dataset` в короткой транзакции BEGIN IMMEDIATE повторно вычисляет inserted/updated/unchanged, регистрирует новые версии и необходимые материалы, затем вставляет завершённый import_log. Любая ошибка откатывает всё, включая журнал и изменение прежних связей/счётчиков. Invalid-набор не фиксируется частично. Активный queued/running run даёт RUN_ACTIVE. Бюджеты, подписи файлов и порядок работы интерфейса остаются сервисом импорта участника 1.

Повтор с новым request UUID возвращает unchanged и добавляет одну запись о завершившемся запросе. Точное повторение с тем же registration_id возвращает прежний ImportResult; другое содержимое под тем же ID даёт REGISTRATION_CONFLICT. Время импорта, dataset_id и серверный storage_path не входят в content_hash источника. Учитываются текст, created_at, requester_id, product/source и отсортированные ID/хеши/значимые метаданные материалов. Совпадение текста у разных source_id не удаляет обращения.

Несколько операций можно объединить:

```python
with repo.transaction() as tx:
    result = tx.register_dataset(batch, registration_id=server_request_uuid)
    # Другие необходимые записи SQLite через tx, без сетевых/файловых операций.
# Успешный HTTP-ответ допустим после выхода из with, когда commit завершён.
```

Файлы и SQLite **не имеют общей транзакции**. При ошибке до commit участник 1 убирает только новые файлы своего запроса. При сбое после перемещения до commit могут остаться бесхозные файлы. `repo.registered_materials()` возвращает полный реестр зарегистрированных путей, в том числе используемых историческими версиями; его можно применять для стартовой сверки и очистки только незарегистрированных остатков. При совпавшем содержимом сохраняется прежний зарегистрированный путь; новый лишний подготовленный файл не регистрируется. Не удаляйте зарегистрированный материал старой версии. При потере ответа после commit повтор не создаёт дублей.

## Источники, нормализация и потребности

`get_source(source_id, product_id="webneft", version=None)` возвращает текущую или конкретную версию. `get_source_history(...)` возвращает все версии. До нормализации `document=null`, `requires_analysis=true`; это не отсутствие потребности. `source_version`, content_hash и provenance доступны явно. `source_materials(..., version=...)` возвращает материалы выбранной версии.

Изменение содержимого добавляет версию, оставляет прежние тексты/фрагменты/потребности и решения тем, исключает старые потребности из активных счётчиков. Прежние ручные переопределения и review помечаются requires_recheck. В затронутых темах увеличивается version, а `TopicDetail.pending_source_ids` показывает источники, ожидающие нового извлечения. Старые карточки нельзя сохранять с прежней version. Текст summary автоматически не генерируется: сервис карточек должен обновить описание после нового анализа и показать неполное покрытие.

`save_normalized_document(document)` связывает фрагменты с текущими product/source/version/hash и проверяет регистрацию asset_id. Маскирование выполняет участник 1 до передачи документа. `save_needs(product_id, source_id, version, needs)` проверяет принадлежность фрагментов и точное вхождение цитат в нормализованный текст. `save_source_analysis(document, needs)` объединяет обе операции в одну транзакцию. Пустой успешный результат отличается от ошибок в document.errors; при ошибке requires_analysis остаётся true.

ASR-фрагмент допускается только для зарегистрированного audio, vision — для image. Ошибка обработки тоже не может ссылаться на asset_id другого источника или незарегистрированный материал. Это проверки ссылочной целостности метаданных; сигнатуры и содержимое файлов остаются участником 1.

`normalization_history(...)` хранит прежние результаты. До использования фрагментов потребностями можно сохранить исправленный результат, включая повтор после ошибки распознавания. Когда результат уже используется потребностями, другое содержимое нормализации и другое успешное извлечение для той же версии источника возвращают явные NORMALIZATION_CONFLICT/ANALYSIS_CONFLICT. Это защищает опубликованные связи и ручные правки; версионирование произвольного повторного анализа с новыми промптами — отдельная задача pipeline, не скрытая перезапись.

## Темы, решения и ручные действия

`create_topic(topic, synthetic=None, origin="authored", analysis_mode=None)` создаёт постоянную новую тему из сохранённых активных потребностей с проверенными доказательствами. Признак synthetic выводится из источников; противоречащий ему явный флаг отвергается. При чтении учитываются также исторические синтетические свидетельства: удаление активной связи не превращает искусственный пример в статистику компании. `attach_needs(topic_id, need_ids, expected_version=...)` добавляет свидетельства, сохраняя бизнес-решение. Один source_id считается один раз даже при нескольких потребностях. Счётчики не кэшируются в отдельной таблице: они вычисляются по активным записям. Без полного набора requester_id число заявителей — null.

Для человеческого решения создать отдельную тему после исключения передайте manual_author и manual_reason в create_topic. Создание, связи и attach-переопределения фиксируются одной транзакцией; прежнее исключение остаётся в истории. Без автора/причины вызов отклоняется. Автоматическое создание по-прежнему не обходит ручной запрет. Политика принятия решения и проверка review.version остаются участником 2.

`record_decision(topic_id, DecisionUpdate)` хранит все согласованные бизнес-состояния кроме merged, проверяет version и обязательные поля, атомарно записывает состояние и DecisionEvent. Переходы merged/merge относятся к следующему пользовательскому сервису. HTTP PATCH этапа 1 всё ещё поддерживает только needs_research; сохранение других корректных статусов доступно репозиторию, а не новому экрану. Бизнес-отказ не создаёт ошибку анализа. Сигналы deferred/implemented считаются из сохранённых дат и created_at обращений.

`update_passport(topic_id, passport, expected_version=..., author=..., reason=..., title=...)` сохраняет ручную правку с историей, версиями темы/паспорта и прежним ID/решением. `catalog_snapshot(product_id)` возвращает согласованный снимок немерженных тем и catalog_revision. Ревизию меняет создание/правка паспорта, а обычное решение — нет. Лексический поиск и match/review/new остаются участником 2.

`record_override(ManualOverride, expected_versions={topic_id: version, ...})` сохраняет неизменяемое ручное событие attach/exclude/insufficient_data для конкретной версии источника, меняет активные связи и фиксирует историю всех затронутых тем. Для переназначения нужны актуальные версии исходной и целевой темы. Автоматический attach не отменяет ручное исключение; точный повтор override_id не создаёт второе событие. `get_overrides(...)` и `topic_changes(topic_id)` возвращают историю. Правила постановки в review реализует участник 2; сохранение переопределения и review нужно объединять через repo.transaction.

## Review и запуски

`save_review(ReviewItem, expected_version=None)` создаёт открытый review v1 или сохраняет следующую версию с защитой от конфликтов; `get_review`, `list_reviews`, `review_history` читают состояние и историю. Повтор того же результата идемпотентен. Сохранение review само не выполняет attach/create: это политика участника 2, которая объединит необходимые repository-операции одной транзакцией. Устаревший review не переносится на новую версию источника.

`create_run(Run)` регистрирует queued и при повторном старте возвращает единственный активный run. `get_run`, `save_run` сохраняют прогресс и проверяют переходы/режим/счётчики; терминальное состояние нельзя переписать. `interrupt_active_runs()` переводит незавершённые записи в interrupted; он вызывается при старте однопроцессного приложения, а не при каждом init-db. Это восстановление записей, не работающий worker. Выполнение этапов, checkpoints/cache, POST /runs и настоящий replay остаются следующей задачей.

total_materials нельзя уменьшать: оставшиеся необработанные материалы не могут исчезнуть из отчёта за счёт ложного completed. Общее число и обработанные счётчики остаются согласованными с покрытием и состоянием запуска.
