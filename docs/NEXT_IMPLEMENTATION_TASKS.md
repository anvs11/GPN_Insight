## A1. Зафиксировать совместимые контракты partial processing и классификации

Запрос для реализации: «Прочитай общий ExecPlan, MEDIA_ANALYSIS_HANDOFF и NEXT_IMPLEMENTATION_TASKS. Зафиксируй shared result/coverage/analysis-revision контракт частичной обработки и отдельный контракт категории/приоритета со словарём пользователя. Сохрани старые DTO/HTTP/text replay/checkpoints: расширение должно иметь явную версию. Подготовь JSON-примеры для У2/У4, схему перехода и проверки без сброса SQLite. Не меняй алгоритмы/промпты У2 без передачи контракта».

В полном сохранённом NormalizedDocument остаются успешные masked fragments и все MaterialError. Для анализа допустим только проверенный набор успешных фрагментов; ошибка не исчезает из сохранённого результата/API/отчёта. При отсутствии пригодного контекста — явный исход без успешного extraction; если модель не выделила needs из успешного текста — это другой случай. Фрагменты неуспешного asset не участвуют в цитатах. Для старых профилей сохраняется прежний отказ; новая политика получает новую версию/hash. Не подавлять errors через слепое model_copy.

До кода определить два уровня: число обращений с полным/частичным/нулевым покрытием и число успешных/ошибочных материалов. Нынешние поля Run `total_materials/successful_materials/failed_materials/coverage` фактически считают источники, не каждый asset; не менять их смысл без версии. Подготовить аддитивные явные счётчики/единицы и их проверку в UI. Политика partial утверждена, а новые поля/миграция ещё не реализованы.

Главная граница хранения: нынешние опубликованные NormalizedDocument/needs неизменны для того же ключа, а успешный extraction checkpoint сейчас привязан к source/profile. Если после частичного результата позже распозналось ещё вложение, нельзя просто перезаписать прежний документ или повторить старый extraction как полный. Нужна версия результата/analysis revision либо эквивалентная версионированная связь с digest набора успешных фрагментов и покрытия. Нельзя создавать новую исходную source_version только ради retry распознавания. У3 проектирует атомарную публикацию нового результата с сохранением decision/passport/history/overrides; без этого не включать partial production.

Готовность: примеры «text+ошибка аудио», «успешное аудио+ошибка картинки», «все неуспешны», «retry дополнил контекст», «старый профиль» проходят validation; доказательства не могут ссылаться на failed/чужой фрагмент; неизвестная оценка и техническая ошибка различаются. У2 получает конкретный интерфейс анализа успешного контекста, У4 — read/progress примеры до UI.

## A3. Часть У1 и У3: мультимодальный Normalizer и строгий media replay

Запрос: «Реализуй media Normalizer и ASR/VL replay на существующих ApprovedAsset/MediaText/RecordingMeta, по версии контракта A1. Бери постоянный файл только через resolve_registered_asset с точной версией источника. Сохраняй успешный текст и фрагменты независимо от ошибки другого вложения, маскируй до сохранения/текстового запроса/recording. Проверяй asset kind/ID, quote context и временные метки. Live оставь явно недоступным. Добавь известные synthetic authored recordings четырёх поддерживаемых форматов и отдельную процедуру их проверки; не выдавай их за распознавание реальной модели».

Ключ media request включает точный content hash, операцию, MIME, schema/version, recipe/masking version, модель/параметры и recording_set_version. Файловый путь не заменяет идентичность; binary bytes не копируются в JSON recording. Неизвестный запрос/некорректное происхождение/схема/параметры — явная ошибка без похожей записи/сети. Сохранённый текст и вход анализа одинаковы; live origin=authored запрещён. Для authored компонентов использовать явно synthetic имена, не притворяться проверенными реальными ASR model ID.

Успешные material checkpoints независимы по source/version/asset/hash/profile. При повторе не распознавать успешный asset заново; восстановление после сбоя и дополнение контекста проходят A1 revision. Стабильность fragment ID новой media-policy должна учитывать asset/segment, а не только меняющийся порядковый индекс успешных фрагментов. Старые text ID/key и существующие sets не переписывать. Gateway безопасно переоткрывает/сверяет bytes непосредственно перед чтением; root/hash/owner resolver не заменяется клиентским URL.

Готовность: WAV/MP3/PNG/JPEG с known authored outputs, text+media, несколько вложений, пустой успешный результат/ошибка, подмена файла, чужой asset, timestamps, partial retry/restart и provenance. Production media guard снимается только после A4, а не ради прохождения unit-test adapter.

## A4. Часть У3: включить partial pipeline без потери решений

Запрос: «Подключи A3 к обычному bootstrap через явный media ProcessingProfile и A1 revision/coverage. Сначала нормализуй все источники, затем анализируй пригодный успешный контекст в прежнем установленном порядке. Полный сохранённый результат содержит errors, анализ получает только проверенные success fragments, каждый need ссылается на них. Опубликуй согласованную ревизию атомарно, сохрани decision/passport/history/overrides и видимые pending/recheck. Не сбрасывай старые данные и не меняй контракт импорта».

При новой успешной расшифровке меняется digest аналитического входа, поэтому старый extraction checkpoint не переиспользуется как итог полного контекста. Успехи распознавания и прежние ручные решения сохраняются; новые/исчезнувшие needs и связи обрабатываются по revision policy, не через безусловный attach/дублирование counts. Если бизнес-сохранение не завершилось, rollback касается публикации/связей/счётчиков, а не притворного отката файлов. Два прохода/один worker/import guard и explicit unavailable live сохраняются.

Готовность: после первой partial обработки есть подтверждённая тема из успешной части и видимая ошибка; после retry контекст дополняется без дублирования success/источников и потери решения; после настоящего process restart interrupted/reuse подтверждены. Полный failure не называется «потребностей нет», partial run не называется full completed. Нет скрытого fallback/тестового gateway в main.
