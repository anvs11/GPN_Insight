Подготовь два сопоставимых синтетических пакета и протокол перекрёстного сравнения ручного разбора/карточек двумя проверяющими. Время проверки источников, review и исправлений входит в активное время; ожидание модели учитывается отдельно.

Запрос после фактического измерения:

> Внеси в EFFECT.md только предоставленные или реально измеренные значения, сохрани четыре исходных наблюдения, размер пакетов, качество, происхождение данных и режим live/replay. Рассчитай r при сопоставимом качестве и только допустимые сценарии с источниками/помеченными допущениями. Не масштабируй синтетический эксперимент на компанию без основания. Подготовь три сценария и чувствительность к двум наиболее влиятельным параметрам, проверь a=0 и k=0. Трёхлетнюю границу инвестиций выводи из денежных выгод отдельных лет с постепенным запуском; без механизма денежной экономии оставь её неподтверждённой. Синхронизируй относящиеся выводы с участниками 3 и 4, не объявляй расчёт доказанной окупаемостью.

Готовность: репетиция протокола к дню 5, основное измерение на дне 7, заморозка допущений на дне 8. Методика эффекта не заменяет отдельный конкурсный документ с метриками качества. На дни 8–9 новые функции не планируются.

## Шаг 10. Общая приёмка и передача — дни 5–7

Запрос:

> Проверь блок участника 1 в общем сценарии GPN Insight: веб-preview → импорт → нормализация/анализ → источник → решение → повтор → delta. Работай с отдельной тестовой БД и согласованной синтетикой. С участником 3 проверь регистрацию, аварийные границы, рестарт и отсутствие потери решений; с участником 2 — цитаты, ошибки распознавания, маскирование и инъекции через три канала; с участником 4 — фактическое отображение источников и ошибок. Проверь одинаковые правила браузера и CLI. Выполни относящиеся тесты, затем существующий backend-набор и валидацию примеров. Если pipeline, frontend, replay или модели ещё не подключены, перечисли конкретный незавершённый участок и проверь независимую часть; не объявляй весь путь пройденным. Новые функции не добавляй. Обнови Progress, открытия, решения и Outcomes фактическими результатами.

Для уже существующих проверок из `backend/` в PowerShell:

```powershell
..\.venv\Scripts\python.exe -m pytest -q
..\.venv\Scripts\python.exe -X utf8 -m app.cli validate-examples
```

На macOS/Linux, также из `backend/`, после подготовки поддерживаемого окружения по README:

```sh
../.venv/bin/python -m pytest -q
../.venv/bin/python -m app.cli validate-examples
```

Backend проверен командой на Python 3.13.0 в прежней Windows-среде; наличие такого окружения на другой машине проверяется отдельно. Установку выполнять по актуальному README и lock-файлу. Команды `import`, `run`, `probe-models` и `verify-recordings` из целевого ExecPlan использовать только после проверки, что они реализованы: сейчас наличие их описания не подтверждает наличие CLI-команды. Точное число тестов и результаты каждой проверки записывать после запуска.

## Как завершать каждый небольшой этап

После реализации просмотреть diff и самому выполнить главное действие этапа. Подходящий запрос:

> Проверь текущий diff как ревьюер блока участника 1: обход валидации/лимитов, чтение произвольных путей, утечки ПДн в нормализацию/replay/логи, дубли, потерю решений, ошибочную очистку зарегистрированных файлов, скрытые ошибки медиа и незавершённые интеграции. Исправь проблемы в пределах задачи, выполни нужные проверки и обнови ExecPlan. Покажи состав небольшого коммита, краткое описание PR и команды ручной проверки. Не выполняй commit, push, merge или публикацию без отдельного поручения.

Самостоятельно посмотреть изменения из корня:

```text
git status --short
git diff
git diff --cached
```

Для локальной фиксации после просмотра состава можно дать отдельное поручение:

> Создай локальный коммит только с проверенными изменениями этого этапа и относящейся документацией. Используй явный список путей; не включай чужие изменения, реальные обращения, .env, базы, временные файлы и отчёты var/. Покажи результат. На GitHub не отправляй.

Push и открытие PR — отдельное поручение после проверки. Merge выполняет уполномоченный участник команды. Не выполнять pull, reset или перенос веток поверх незавершённых изменений без проверки их владельца и состава.

## Минимальный результат, который передать товарищам первым

Первым передать небольшой проверенный текстовый импорт: общий сервис для preview/фиксации, четыре синтетических обращения, повтор с unchanged, понятные ошибки и точный способ проверки на отдельной БД. Участнику 3 нужны точки подключения CLI/HTTP и результаты проверки регистрации; участнику 2 — замаскированный NormalizedDocument и происхождение фрагментов, когда готов шаг 4; участнику 4 — реальные preview/result и ошибки, когда готов шаг 5. Для этого не требуется ждать ASR/VL, полного набора данных или завершённого финансового расчёта.

Локальный файл или коммит ещё не означает, что товарищи получили результат. Передачу общей версии фиксировать после разрешённой отправки и принятия небольшого PR. После каждого этапа сверять дальнейшие шаги с актуальным ExecPlan, а не выполнять устаревшую памятку автоматически.
