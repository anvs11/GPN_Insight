# GPN Insight — Frontend, текущий проверяемый срез

На 2026-11-06 работает панель состояния и запусков через реальные `/api/v1/health`, `POST /api/v1/runs` и `GET /api/v1/runs/{run_id}`; подключены список, карточка, источники и сохранение решения. Локальная frontend обновлена до main `2afa4311`: компоненты анализа участника 2 появились, но обычный Backend ещё не подключён к нормализации и анализу — `pipeline_ready=false`, попытка запуска даёт `503 INTEGRATION_NOT_READY` без создания run. Это не мешает читать сохранённые темы и сохранять решения. Типы ответов находятся в `src/api-types.ts`, все запросы — в `src/api.ts`. Импорт из отдельных веток не подключён.

Статичный макет «Экспорт списка заявок» заменён списком из Backend. По умолчанию сервер отдаёт только повторяющиеся немерженные темы за всё время; фильтра периода у этого списка нет. Показаны название, статус и ответственный, программные счётчики обращений/заявителей, synthetic/authored/model, режимы сервера/анализа и предупреждение о pending_source_ids. Отсутствующее число заявителей остаётся «Нет данных». `TopicListItem` — проекция отображаемых полей `TopicDetail`, а не новый серверный формат. Несоответствующий ответ не превращается в пустой список. При ошибке обновления последний успешный список остаётся с предупреждением о неактуальности.

По нажатию на название загружается подробная карточка `GET /api/v1/topics/{topic_id}`: описание и границы потребности, серверные показатели, статус, версии, подтверждающие цитаты и история решений только для просмотра. Кнопки источников отдельно читают `GET /api/v1/sources/{source_id}` — текущую версию обращения, не архивную версию цитаты. Совпадение цитаты проверяется только в указанном сервером фрагменте; несовпадение явно требует проверки и не заменяется выдуманным доказательством. Это проверка текста, не качества вывода. Источник показывает фрагменты, предупреждения/ошибки, потребности и метаданные вложений; HTTP API получения самих файлов пока не подключён. Исходный текст показывается только для synthetic=true; доступ к оригиналам несинтетических данных требует отдельного согласования. Тексты отображаются как текст, HTML/Markdown не исполняется.

Загрузка и ошибки карточки/источника независимы от списка: 404 не заменяется встроенным примером, при отказе обновления последние прочитанные данные сохраняются с предупреждением. При смене темы или источника прежний запрос отменяется, запоздалый ответ игнорируется. Пустой/необработанный источник не объявляется обращением без потребностей. Синтетические демонстрационные данные явно подписаны и не выдаются за статистику компании.

В карточке есть форма `PATCH /api/v1/topics/{topic_id}/decision`: только `new/needs_research`, непустые owner/reason и целая текущая version. Оба целевых статуса допустимы из любого немерженного состояния; внутри двух поддерживаемых статусов допустимы все четыре сочетания, включая сохранение того же статуса. Каждый принятый PATCH добавляет DecisionEvent и повышает версию на 1. Для merged форма блокируется и показывает основную тему. Остальные статусы в форму не добавлены.

Ответ PATCH проверяется по контракту и ожидаемому изменению. Затем выполняется отдельный GET карточки: проверяются статус/владелец, версия, новая запись решения и неизменность каждого прежнего события истории. Только после этого появляется подтверждение, карточка и строка списка обновляются серверными данными. Если после нашего события уже сохранено другое решение, интерфейс показывает его как более позднее изменение, не выдавая наш статус за текущий.

409 сохраняет черновик, перечитывает карточку и требует явной кнопки «Использовать версию … для нового сохранения» после проверки актуальных данных. Автоматического повторного PATCH нет. 422/404 и сетевые ошибки видны, введённые поля не сбрасываются. Неопределённый ответ PATCH сначала проверяется GET, поскольку запись могла завершиться. При принятом PATCH и отказе повторного GET доступна отдельная кнопка проверки; повторный PATCH заблокирован. При неполном подтверждении истории успех не показывается. Во время запроса поля и повторная отправка блокируются; ref защищает также два submit до следующего рендера React.

Черновик существует в открытой карточке и переживает её обновление и ошибки. Закрытие карточки или перезагрузка страницы сбрасывает несохранённый черновик; долговременное хранение текста решения в браузере не добавлено. Сохранённое решение хранится Backend в SQLite и читается после перезагрузки/рестарта. Первый этап целиком не объявляется завершённым: импорт, полный анализ, медиа и остальные действия остаются открытыми. Синтетические ответы UI-тестов не используются приложением как fallback.

## Запуск в Windows PowerShell

Нужны уже подготовленная `.venv` в корне и зависимости Frontend. Их версии в этой задаче не менялись. Если зависимости Frontend отсутствуют, из `frontend/` выполните `npm ci`; для установки Backend используйте закреплённый `backend/requirements.txt` по корневому README.

Терминал 1 — Backend. Для проверки выбрана отдельная база; `.env` и прежняя рабочая база не меняются:

```powershell
Set-Location 'D:\Python\Кейс ГЗ\GPN_Insight\backend'
$env:APP_DB_PATH = 'var/frontend-local-check.db'
$env:APP_MODEL_MODE = 'replay'
..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Ожидается `Uvicorn running on http://127.0.0.1:8000`. Переменные `$env:` здесь действуют в этом терминале и его дочерних процессах; системные настройки и файл `.env` не редактируются. При повторном запуске используйте то же имя базы, чтобы видеть прежнее состояние. Команда не импортирует данные и не вызывает модели.

Терминал 2 — Frontend:

```powershell
Set-Location 'D:\Python\Кейс ГЗ\GPN_Insight\frontend'
npm run dev
```

Ожидается `Local: http://127.0.0.1:5173/`. Откройте этот адрес вручную. Порт 5173 фиксирован: при занятости Vite сообщит ошибку, а не сменит адрес. `/api` передаётся на `127.0.0.1:8000`; CORS и внешние сервисы не нужны. Корень Backend на 8000 пока не отдаёт собранный Frontend и отвечает 404 — это отдельное незавершённое требование итоговой сборки. `npm run preview` не заменяет эту проверку: для API здесь настроен именно dev-прокси.

Оба терминала оставьте открытыми. Для остановки своего сервера нажмите `Ctrl+C` в соответствующем терминале. Если сервер уже запущен, вторую копию не запускайте.

## Ручная проверка в браузере

Пользователь подтвердил ручную визуальную приёмку панели и всего второго этапа без замечаний. Инструкция ниже сохранена для повторного запуска; автоматической браузерной проверкой это подтверждение не считается. Заключительные исправления гонок и показа подтверждения проверены автоматическими регрессиями, оформление интерфейса не менялось.

1. Откройте `http://127.0.0.1:5173/`. Ожидаются заголовок GPN Insight и панель «Состояние обработки». После ответа сервера видны «Доступен», режим `replay`, свободный обработчик и сообщение «Обработка пока недоступна: интеграция не завершена». Рядом перечислены неподключённые компоненты 1/2. Кнопка запуска недоступна; фиктивного успешного запуска нет.
2. Раскройте «Модели и сохранённые ответы». При стандартной конфигурации записей нет, текст сообщает `REPLAY_NOT_CONFIGURED`, речь/изображения — `REPLAY_NOT_IMPLEMENTED`. Если вы заранее настроили настоящий набор, сведения могут отличаться: они берутся с сервера. Выбранный режим не доказывает доступность моделей.
3. Введите период `01.10.2026`–`31.10.2026`, нажмите Tab после ввода и обновите страницу в той же вкладке. Обе даты должны сохраниться. Даты трактуются по Москве, обе границы включены. Поставьте начало позже окончания: должна появиться ошибка периода. Затем верните правильные даты.
4. В поле ID введите `frontend-review-missing` и нажмите «Показать запуск». Должны появиться `HTTP 404 · RUN_NOT_FOUND` и сообщение сервера. Введённый ID остаётся в поле; новый результат не выдумывается. Если до проверки уже был открыт настоящий запуск, его последние данные подписаны как не обновлённые. Только последний успешно открытый ID сохраняется между перезагрузками, произвольный неизвестный ID — нет.
5. Остановите свой Backend через `Ctrl+C` в терминале 1, оставив Frontend открытым. Нажмите «Обновить состояние». Должна появиться ошибка соединения или ответа прокси с подсказкой проверить Backend. Отметка «Доступен» исчезает, запуск блокируется, введённый период сохраняется. Переключения на другой режим и фиктивных результатов нет.
6. В том же терминале 1 повторите команду Uvicorn, не меняя `APP_DB_PATH`. Нажмите «Обновить состояние» в браузере. Сервер снова должен стать доступен, а незавершённая интеграция остаться явно обозначенной. Ошибка проверки сервера исчезает, период сохраняется.
7. Под панелью должна появиться секция «Темы из обращений». В новой пустой базе ожидается сообщение «Повторяющихся тем пока нет», а не статичный пример. Для проверки наполненного списка используйте отдельную синтетическую базу ниже. Уменьшите ширину окна примерно до 390 пикселей: проверьте читаемость, поля/кнопки и отсутствие горизонтального обрезания. Клавишей Tab проверьте видимое выделение интерактивных элементов.

## Проверка списка на отдельной синтетической базе

Остановите свой Backend через Ctrl+C. В терминале Backend выполните:

```powershell
Set-Location 'D:\Python\Кейс ГЗ\GPN_Insight\backend'
$env:APP_DB_PATH = 'var/frontend-topics-demo.db'
$env:APP_MODEL_MODE = 'replay'
..\.venv\Scripts\python.exe -X utf8 -m app.cli init-db
..\.venv\Scripts\python.exe -X utf8 -m app.cli seed-demo
..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

`seed-demo` явно загружает подготовленные synthetic/authored-данные, модели не вызываются. Он не заменяет обычный импорт. Повтор известного набора безопасен; при ошибке seed не продолжайте запуск с неподтверждённым набором и не сбрасывайте старую базу. Все проверки здесь относятся к указанной отдельной БД.

В браузере нажмите «Обновить список». Ожидается одна тема «Контактный телефон в оформленной заявке», 4 обращения, «Нет данных» для заявителей и явные подписи синтетики/ручной подготовки. На новой базе статус «Новая», ответственный не назначен; если в этой базе уже сохранено решение, список показывает именно его. При analysis_mode=null модельный анализ не подтверждается. Неготовая обработка в верхней панели должна оставаться видимой и не блокировать чтение списка.

Проверьте обновление и отказ: задайте дату в панели обработки, остановите только Backend и нажмите «Обновить список». Ожидаются ошибка и предупреждение «Показан последний полученный список. Обновление не подтверждено»; тема и дата сохраняются. Перезапустите Backend с тем же APP_DB_PATH и повторите чтение: ошибка должна исчезнуть, счётчики остаться прежними.

## Ручная проверка карточки и источников

Пользователь подтвердил успешную ручную визуальную проверку всех сценариев второго этапа, включая карточку, источники, решения и конфликты. Это ручная приёмка, а не автоматический браузерный тест. Ниже сохранена инструкция для воспроизведения с отдельной `var/frontend-topics-demo.db` и Frontend на `http://127.0.0.1:5173/`.

1. Откройте вкладку браузера, нажмите F12 → Network (Сеть) и выберите Fetch/XHR. Нажмите название «Контактный телефон в оформленной заявке». Под темой должна открыться секция «Карточка темы». В Network появится GET `/api/v1/topics/{topic_id}` с HTTP 200. При медленном ответе видна надпись «Загружаем карточку…», а не фиктивная карточка.
2. Сверьте данные с вкладкой Response (Ответ) запроса: потребность/сценарий/границы, версия темы и паспорта, статус, ответственный, 4 обращения, отсутствие данных о заявителях, даты и недели. На новой фикстуре история пуста; существующее решение в этой демонстрационной базе должно показываться без изменений. Все показатели приходят с Backend; число источников на экране не подменяет серверный счётчик.
3. Убедитесь, что видны «Синтетические демонстрационные данные — не статистика компании», ручное происхождение authored, режим replay и отсутствие подтверждённого модельного анализа. Верхняя панель по-прежнему показывает незавершённую интеграцию; это не мешает читать карточку.
4. В разделе «Подтверждающие обращения» нажмите «Проверить источник …». Должен появиться GET `/api/v1/sources/{source_id}` с HTTP 200 и секция источника. Видны его ID, версия, дата, синтетическое происхождение, исходный текст и подготовленные фрагменты. Цитата сверяется с указанным фрагментом текущей версии. В этом текстовом наборе вложений нет; аудиоплеер и просмотр изображения не заявляются.
5. Нажмите кнопку другого обращения: секция должна показать именно его ID/текст. Кнопки «Открыть обращение …» читают источник без выбора отдельной цитаты. «Закрыть источник» оставляет карточку и список. «Закрыть карточку» оставляет весь список и панель. Повторный выбор темы заново читает сервер.
6. Задайте дату в панели обработки. При открытых карточке и источнике остановите только свой Backend через Ctrl+C. Нажмите «Обновить источник»: ожидается видимая ошибка соединения/ответа прокси и предупреждение о последнем полученном источнике; карточка, список и дата остаются. Если источник открыт из цитаты, во время загрузки и после отказа должно быть «Сверка цитаты с текущей версией источника не подтверждена», а не подтверждение по старому фрагменту. Затем нажмите «Обновить карточку»: источник закрывается, последнее содержимое карточки остаётся с предупреждением. Ошибка не превращается в пустые данные и не меняет режим.
7. При остановленном Backend закройте и вновь откройте карточку. Теперь должно быть сообщение об ошибке без карточки-примера, а список и дата должны сохраниться. Повторите запуск Uvicorn в том же PowerShell с тем же APP_DB_PATH. Нажмите «Обновить карточку», затем откройте источник. Ошибки должны исчезнуть, счётчики/версии/сохранённые решения остаться прежними.
8. В Network проверьте, что открытие/обновление карточки и источников отправляет только GET. PATCH отправляется отдельно формой решения по сценарию ниже. «История решений» раскрывается только для чтения; нормальный пустой ответ явно обозначен.
9. Уменьшите окно примерно до 390 px, проверьте перенос длинных ID/цитат и отсутствие горизонтального обрезания. Проверьте светлую и тёмную системные темы. Клавишами Tab и Enter откройте тему/источник и убедитесь, что выделение кнопок видно.

404 карточки и источника, повреждённый ответ, отсутствие документов/цитат и ошибки распознавания проверены автоматическими тестами; стандартный seed-demo не создаёт эти состояния. Без изменения данных их можно дополнительно проверить как HTTP-контракты из отдельного PowerShell:

```powershell
foreach ($resource in 'topics', 'sources') {
    try {
        Invoke-RestMethod ('http://127.0.0.1:8000/api/v1/' + $resource + '/frontend-review-missing')
    } catch {
        if ($null -eq $_.Exception.Response) { throw }
        Write-Output ('HTTP ' + [int]$_.Exception.Response.StatusCode)
        Write-Output $_.ErrorDetails.Message
    }
}
```

Ожидаются HTTP 404 с TOPIC_NOT_FOUND и SOURCE_NOT_FOUND. Это проверка API, а не визуальное воспроизведение 404; удалять тему или править БД для проверки интерфейса не нужно.

Период и последний успешно открытый ID хранятся в `sessionStorage` только этой вкладки. Закрытие вкладки может удалить их; долговременное сохранение не заявляется. Другие ключи хранилища и настройки пользователя компонент не очищает. Кнопка запуска не отправляет запрос при `pipeline_ready=false`, поэтому ветка UI с неожиданным 503 проверяется тестом с устаревшей готовностью, без изменения настоящего Backend.

Отдельно проверить фактический отказ API можно в свободном PowerShell-терминале при работающем Backend:

```powershell
try {
    Invoke-RestMethod 'http://127.0.0.1:8000/api/v1/runs' `
        -Method Post -ContentType 'application/json' -Body '{"product_id":"webneft"}'
} catch {
    if ($null -eq $_.Exception.Response) { throw }
    Write-Output ('HTTP ' + [int]$_.Exception.Response.StatusCode)
    Write-Output $_.ErrorDetails.Message
}
```

Ожидаются HTTP 503 и JSON с `code=INTEGRATION_NOT_READY`, а не успешный запуск. В интерфейсе нет переключателя live/replay: режим задаёт Backend. Если вы явно перезапустите свой сервер с `APP_MODEL_MODE=live`, панель должна показать live и фактические ограничения моделей; автоматически переходить в replay она не должна.

## Ручная проверка сохранения решения

Используйте отдельную `var/frontend-topics-demo.db` из команд выше. Не проводите проверку конфликтов на рабочей базе. Если Backend уже запущен, остановите именно свой процесс через Ctrl+C перед повторным стартом. При ошибке init-db/seed-demo остановитесь, не сбрасывайте базу и не продолжайте с неподтверждённым набором.

1. Откройте `http://127.0.0.1:5173/`, нажмите название темы. В карточке должна быть форма «Решение владельца продукта». Запишите текущую версию N и число событий H. На новой синтетической базе это N=1, H=0; существующее решение не сбрасывается seed-demo. Выбор статуса содержит только «Новая» и «Исследуется». Маркировка synthetic/authored/replay и незавершённая интеграция остаются видимыми.
2. Откройте F12 → Network → Fetch/XHR. Выберите «Исследуется», укажите ответственного «Синтетический владелец 4» и причину «Проверил подтверждающие обращения». Нажмите «Сохранить решение». Во время запроса поля и кнопка заблокированы; при медленном ответе видны «Сохраняем решение…», затем «Проверяем карточку…». Не должно быть подтверждения до окончания второго запроса.
3. В Network ожидаются PATCH `/api/v1/topics/{topic_id}/decision` с четырьмя полями status/owner/reason/version=N и затем GET `/api/v1/topics/{topic_id}`, оба HTTP 200. После GET появится «Сохранение подтверждено повторным чтением», версия N+1, история H+1, статус/ответственный обновятся также в строке списка. Раскройте историю: прежние события сохранены, новая причина и владелец совпадают с вводом. Счётчик остаётся 4 обращения, заявители — «Нет данных».
4. Для возврата выберите «Новая», измените причину и сохраните. Ожидается ещё одна версия и событие, а не очистка истории. Для повторного решения с тем же статусом измените причину: сервер также добавит событие и версию. Сразу после подтверждённого сохранения та же неизменённая форма заблокирована от случайного повтора; изменение полей разрешает новое осознанное решение.
5. Перезагрузите страницу, снова откройте тему: статус/ответственный/версия/история должны сохраниться. Затем остановите Backend и запустите ту же команду Uvicorn в том же PowerShell с прежним APP_DB_PATH. Обновите список и откройте карточку — сохранённое решение должно остаться. Не генерируйте новый путь базы для проверки рестарта.
6. Проверьте конфликт двух вкладок. В A и B откройте одну тему с одной версией. В A заполните своё решение и оставьте его неотправленным. В B сохраните решение с другим ответственным и причиной. Затем отправьте форму A: ожидаются HTTP 409 VERSION_CONFLICT и GET актуальной карточки. Значения A сохраняются, в карточке/истории видно решение B, повторная отправка заблокирована. Без нажатия «Использовать версию …» нового PATCH быть не должно. Сравните историю и нажмите эту кнопку, затем отдельно «Сохранить решение». Ожидаются новая версия и оба события A/B в истории.
7. Проверьте обязательные поля: очистите ответственного или задайте причину только пробелами. Нажатие сохранения показывает русское сообщение FORM_INVALID и не отправляет PATCH. Не должно появиться нового события или изменения версии. После корректировки поля можно отправить.
8. Проверьте сетевой отказ. При загруженной карточке заполните отличающееся решение, остановите свой Backend и нажмите сохранение. Ожидаются видимые ошибки, отсутствие подтверждения и сохранённые значения. При неопределённом результате повторная отправка блокируется. Перезапустите Backend с тем же APP_DB_PATH и нажмите «Проверить карточку без повторного сохранения»: этот шаг отправляет только GET. Если запись уже существует — она подтверждается без дубля. Если запись не найдена — проверьте текущую карточку и явно примите показанную версию перед отдельной новой попыткой.
9. При успешном PATCH и отказавшем GET используется та же кнопка проверки без повторного PATCH. Этот случай, 422/404, повреждённый ответ и потеря ответа после фактического commit воспроизведены автоматическими проверками: не меняйте Backend и не удаляйте темы ради ручного создания ошибки. Обычная форма сама блокирует пустые поля, поэтому серверный 422 не требуется искусственно обходить через интерфейс.
10. Проверьте Tab/Enter, видимый фокус, перенос длинных причин и окно около 390 px. Убедитесь, что открытие источников и поля панели обработки продолжают работать. Несохранённый черновик сохраняется при ошибках/обновлении открытой карточки; закрытие карточки и F5 сбрасывают именно черновик, не сохранённое сервером решение.
