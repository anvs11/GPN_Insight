## Purpose / Big Picture


В компании обращения в поддержку содержат повторяющиеся некритичные затруднения и пожелания, которые трудно систематически передавать продуктовым командам. После реализации владелец «Вебнефти» сможет открыть внутреннюю страницу, увидеть сгруппированные потребности с подтверждающими обращениями и зафиксировать решение. Поддержке не потребуется вручную размечать каждое обращение.

Главная демонстрация: импортировать набор текстов, звонков и скриншотов; запустить обработку; открыть карточку повторяющейся потребности; проверить источник; сохранить решение; повторить импорт без дублей; добавить новое обращение и увидеть обновление той же карточки с сохранённым решением. Видимые ошибки материалов входят в сценарий проверки.

Работу выполняют четыре человека за девять календарных дней. План предполагает в среднем пять часов сосредоточенной работы каждого в день, то есть примерно 180 человеко-часов до учёта общих встреч. Это плановая оценка доступности, не обещание производительности. В начале первого дня команда уточняет фактическую доступность и записывает её сюда. Последние два дня отведены на стабилизацию, репетиции и резерв.

## Decision Log


Decision: делать один сервер и один веб-интерфейс с пятью логическими компонентами, а не пять независимо разворачиваемых сервисов. Rationale: девять дней и четыре участника требуют ранней сборки; границы импорта, нормализации, анализа, карточек и рассмотрения остаются явными. Дата/автор: 2026-11-03, автор плана. Для итоговой конкурсной архитектуры отдельно обосновать промышленное выделение микросервисов, потому что этот аспект оценивается в постановке.

Decision: использовать Python 3.12, FastAPI, стандартную SQLite и React с TypeScript и Vite. Rationale: один язык для серверной обработки и работы с моделями, минимальная локальная установка хранилища, независимая работа участника интерфейса. Node.js должен удовлетворять требованиям выбранной версии Vite; исходное допущение — Node.js 22.12 или более новая совместимая версия. Дата/автор: 2026-11-03, автор плана. Версии пакетов проверить и зафиксировать в первый день, затем не обновлять без причины.

Decision: сервер использует один процесс, одну последовательную очередь обработки в памяти и сохранённые в SQLite состояния запусков и этапов. Rationale: этого достаточно для небольшой демонстрационной выгрузки; брокер сообщений и отдельная распределённая очередь не нужны. Перезапуск не должен скрывать прерванный запуск. Дата/автор: 2026-11-03, автор плана.

Decision: начать с одного продукта, импорта подготовленной выгрузки и запуска по кнопке. Rationale: доступ к реальной БД не подтверждён, а полезность можно доказать на воспроизводимом наборе. Командный запуск того же процесса позволяет позднее включить внутреннее расписание без отдельной платформы. Дата/автор: 2026-11-03, автор плана.

Decision: сохранить в объёме пилота текст, аудио и изображения; поддержать UTF-8 JSON, WAV/MP3 и PNG/JPEG в пределах проверенных лимитов моделей. Rationale: нельзя считать анализ всех каналов доказанным только по текстам. Произвольные офисные документы, видео и архивы вложений не поддерживаются. Дата/автор: 2026-11-03, автор плана.

Decision: не вводить обязательную модель эмбеддингов. Rationale: наличие модели числового представления текста в кейсе не подтверждено. На малой выборке текстовая модель сопоставляет потребность с сохранёнными темами того же продукта; список кандидатов ограничивается размером проверенного контекста, сомнительные случаи идут на проверку. Дата/автор: 2026-11-03, автор плана. Если нагрузка подтвердит необходимость другого поиска, это отдельное изменение плана.

Decision: иметь два явных режима: live для настоящих вызовов внутренних моделей и replay для воспроизведения сохранённых ответов на известных входах. Rationale: интерфейс и хранение можно разрабатывать без доступа к моделям, а комиссия должна видеть происхождение результата. Автоматического перехода live → replay при ошибке нет. Дата/автор: 2026-11-03, автор плана.

Decision: первоначально разрешить одному тестовому владельцу рассматривать синтетические данные на локальном компьютере. Rationale: полноценная корпоративная авторизация не укладывается в доказательство ключевого сценария. Использование реальных данных и доступ из сети требуют отдельной проверки доступа; локальный режим не называть промышленным внедрением. Дата/автор: 2026-11-03, автор плана.

Decision: отделять бизнес-решение от ошибки анализа и не менять промпты автоматически по пользовательским нажатиям. Rationale: отклонённая реальная потребность не становится ложной. Исправления промптов проверяются на сохранённой выборке. Дата/автор: 2026-11-03, автор плана.

## Context and Orientation


«Вебнефть» — выбранный для пилота B2B-продукт заказа топлива. Пользователь продукта обращается в поддержку; владелец цифрового продукта рассматривает обнаруженные потребности. Эти роли не смешиваются. Пилот не отвечает клиентам и не заменяет обработку инцидентов.

Тикет — одна запись обращения с постоянным source_id. Материал — текст или связанный аудио-/графический файл. Нормализованный документ — текстовая форма материалов с указанием происхождения фрагментов. Потребность — отдельное затруднение или просьба внутри обращения. Тема — сохраняемая группа потребностей одного продукта и пользовательского сценария. Карточка — понятное человеку представление темы с доказательствами. Идемпотентность — возможность повторить импорт и обработку без появления дублей и повторного увеличения счётчиков.

Пилот создаётся в отдельном репозитории с предлагаемым именем gpn-insight-pilot. Во всех командах рабочая папка задаётся относительно этого корня; фактический абсолютный путь команда вписывает при начале работы. Не создавать файлы реализации рядом с исходным проектом soul_game только потому, что там найден PLANS.md.

В корне разместить README.md с запуском, .env.example с названиями настроек без секретов, .gitignore, .agent/PLANS.md и .agent/EXECPLAN.md. Данные демонстрации находятся в data/demo/, расширенная выборка для настройки — в data/development/, независимая выборка — в data/holdout/, сохранённые ответы моделей — в data/recordings/. Файл var/insight.db содержит локальную базу, var/reports/ — результаты проверок и отчёты. Каталог var/ и настоящие секреты не включать в репозиторий.

Сервер находится в backend/. backend/app/main.py создаёт приложение; config.py читает настройки; schemas.py определяет общие структуры; db.py и repositories.py отвечают за хранение; api.py описывает HTTP-интерфейс; pipeline.py выполняет последовательность обработки; gateways.py описывает интерфейсы вызовов моделей; cli.py предоставляет командный запуск. Импорт и форматы находятся в backend/app/ingestion/importer.py и normalizer.py. Анализ находится в backend/app/analysis/extractor.py, grouping.py и cards.py. Промпты хранятся в backend/prompts/extract.md, assign.md и summarize.md. Проверки сервера находятся в backend/tests/.

Интерфейс находится в frontend/. frontend/src/App.tsx связывает экраны, api.ts обращается к серверу; компоненты ImportsPage.tsx, TopicList.tsx, TopicDetail.tsx, SourceViewer.tsx и ReportPage.tsx находятся в frontend/src/components/. Настройка frontend/vite.config.ts передаёт запросы /api к локальному серверу; при демонстрационной сборке сервер отдаёт готовые файлы frontend/dist/. Внешние CDN, шрифты, аналитика и вызовы моделей из браузера не используются.

## Plan of Work


### Milestone 1 — день 1: подтвердить входы и запустить общую основу


Участник 3 создаёт минимальный проект, общие структуры и постоянное хранилище; участник 4 показывает одну тестовую карточку через сервер. Участники 1 и 2 проверяют типовые входы и готовят первые четыре обращения с разными формулировками одной просьбы. К концу дня сервер возвращает состояние, интерфейс открывает карточку и сохраняет решение после перезагрузки страницы.

В первые часы участники 1 и 3 получают реальные настройки трёх моделей от организаторов или владельцев инфраструктуры. Адрес, модель, способ авторизации, метод загрузки аудио/изображений, лимиты, наличие временных меток и фактический формат ответа записываются без секретов в README.md и Surprises & Discoveries. Не предполагать совместимость ASR с текстовым методом chat completions. Вызов probe-models должен отличать недоступность, ошибку авторизации, неподдерживаемый формат и корректный ответ. Если доступ не получен, сразу включить явный replay для разработки; вопрос доступа остаётся открытым, а не помечается решённым.

Наблюдаемая проверка: из backend/ выполнить python -m app.cli init-db и python -m app.cli probe-models --mode live; запустить сервер и открыть /api/v1/health. Состояние моделей может быть unavailable при отсутствии доступа, но это не должно мешать работе replay. Результат дня — работающая основа и известный риск интеграции, а не обещание «подключим потом».


### Milestone 2 — день 2: провести текстовое обращение через весь продукт


Участник 1 реализует импорт JSON и подготовку текста. Участник 2 реализует extract_needs и assign_topic сначала на четырёх известных примерах, затем на переформулировках. Участник 3 связывает импорт, анализ, хранилище и решения. Участник 4 получает карточки по HTTP и сохраняет пользовательское решение через сервер.

Модель должна возвращать структурированные данные, которые проверяются схемой. У каждого извлечённого затруднения есть source_id, исходный фрагмент, тип, сценарий, описание и отдельная гипотеза улучшения. Если модель ссылается на неизвестный источник или цитата отсутствует в подготовленном документе, результат помечается ошибочным и не публикуется как подтверждённое доказательство. Подстрока в расшифровке подтверждает соответствие распознанному тексту, но не доказывает отсутствие ошибки распознавания.

Проверка: импортировать текстовую часть демонстрационного набора, запустить /api/v1/runs, дождаться завершения, открыть тему, выбрать «Исследовать», обновить страницу и перезапустить сервер. Решение сохраняется. Это первая обязательная сквозная сборка; отсутствие аудио на этой стадии допускается и видно в покрытии.


### Milestone 3 — день 3: проверить смысловые группы и повторные запуски


Участник 2 добавляет сравнение с постоянными темами того же продукта; одной общей категории «авторизация» недостаточно для объединения разных затруднений. Если список тем не укладывается в проверенный размер запроса, обработка явно сообщает об ограничении вместо молчаливого игнорирования части тем. Для пилота ограничить прогон 100 обращениями и 50 кандидатными темами одного продукта; эти числа являются техническим ограничением версии и подлежат проверке, а не расчётной мощностью компании.

Участник 3 вводит постоянные topic_id, хеш содержимого источника, версию нормализации и анализа, уникальные связи потребностей и тем. Повторный импорт с тем же source_id и содержимым не создаёт новой записи. При изменении содержимого повторно обрабатывается только изменившаяся запись. Публикация новых потребностей и замена старых связей одного обращения выполняются одной операцией сохранения; частичный сбой оставляет прежний результат с отметкой о неудачном обновлении. Счётчики рассчитываются по активным связям и уникальным source_id, а не по тексту модели.

Участники 1 и 2 заканчивают основную выборку и независимые метки. Участник 4 показывает динамику по неделям без сложной библиотеки визуализации; допустимы обычные столбцы и таблица значений. Проверка: два одинаковых импорта и прогона сохраняют число тикетов и тем; новое обращение по известной теме увеличивает её счётчик на один, сохраняя topic_id и решение. Значение «новая тема» не должно возникать только потому, что модель изменила заголовок.


### Milestone 4 — день 4: включить звонки и скриншоты


Участник 1 подключает ASR и VL через фактические интерфейсы. Он использует короткие записи собственного голоса и искусственные скриншоты, не содержащие настоящих контактов, договоров и доступа. Начальные ограничения пилота: запись до 60 секунд и 10 МБ; изображение до 5 МБ; пределы уточнить по результатам probes и явно отобразить в импорте. Превышение лимита или неизвестный формат получает понятную причину, а не превращается в пустой документ.

Нормализатор объединяет текст обращения и сведения из вложений, сохраняя границы источников. Участник 2 проверяет, что скриншот уточняет контекст, а не создаёт самостоятельную проблему из служебной надписи. Участник 3 публикует состояние каждого материала. Участник 4 показывает расшифровку, изображение и оригинальную демонстрационную запись с проигрыванием; открывать запись с нужного времени только при наличии реальных меток модели.

Проверка: пройти полный набор из 24 обращений, содержащий три звонка и три обращения со скриншотами. В режиме live должны быть настоящие вызовы каждой доступной модели. В replay каждая запись явно помечена как сохранённый ответ. Повреждённая копия файла не мешает обработке остальных материалов; сводка указывает, какая часть набора не обработана.


### Milestone 5 — день 5: завершить цикл рассмотрения


Участник 3 добавляет историю решений и отчёт в Markdown. Участник 4 реализует статусы «Новая», «Исследовать», «Связана с задачей», «Отложена», «Отклонена», поле ответственного и причину решения. Ссылка на задачу — сохранённый текст или разрешённый внутренний URL, а не автоматический запрос во внешнюю систему. Отложенная тема имеет дату пересмотра, которую интерфейс показывает без отдельного планировщика уведомлений.

Обратная связь об ошибке анализа сохраняется отдельным событием: неточная сводка, неверная группа, неверный продукт или неподтверждённый вывод. Участники 2 и 3 добавляют объединение тем и исключение неверно включённых потребностей. Объединённая тема сохраняет ссылку на целевую карточку; исключённые потребности получают ручной запрет на прежнее назначение при повторной обработке неизменившегося источника. Не удалять доказательства и историю без следа. Участник 4 делает эти операции доступными из карточки с предварительным просмотром затрагиваемых элементов.

Проверка: отклонить достоверную тему по бизнес-причине и убедиться, что это не увеличивает счётчик ошибок модели. Объединить два дубликата, исключить неверный фрагмент, перезапустить обработку и убедиться, что ручное исправление сохранено. Скачать сводку: в ней указаны режим, период, покрытие обработки, новые и изменённые темы, решения и источники. Отчёт генерируется из той же базы и не содержит выдуманных чисел.


### Milestone 6 — день 6: измерить качество и устойчивость


Участник 2 запускает независимую проверку; участник 1 сверяет разметку и корректность чтения разных форматов. Сравниваются обнаруженные потребности и группы с заранее сохранёнными метками. Участники 3 и 4 проверяют повторные клики запуска, перезагрузку браузера, перезапуск сервера, тайм-аут модели и пустую выборку. Отдельная проверка подтверждает, что инструкции внутри текста обращения не меняют процесс и не дают доступ к несуществующим инструментам.

Режим live повторяется минимум дважды на одном наборе для выявления нестабильности. Точные значения производительности не назначаются заранее: записываются длительность каждого этапа, общее время, число повторов и причины пропусков. Ошибку сети не считать отсутствием пользовательской потребности. Если качество ниже целевых порогов, разобрать ошибки, скорректировать промпт на development и повторно измерить; набор, по которому уже настраивали модель, больше не называть независимым. В течение девяти дней достаточно честно показать такой переход, если нет времени создать новую независимую выборку.

Проверка: из backend/ выполнить python -m pytest -q и python -m app.cli evaluate с командой из Concrete Steps. Отчёт должен содержать числители, знаменатели, режим и размер выборки. Статус replay запрещает интерпретировать результат как измерение качества живой модели.


### Milestone 7 — день 7: собрать доказательства пользы и конкурсный материал


Участники 3 и 4 завершают сборку для запуска одним сервером; остальные проверяют её из чистой папки и собирают ограничения. Новые функции после этого этапа не добавляются. Разрешены исправления ошибок и сокращение объёма с записью в Decision Log.

Для проверки пользы участники 1 и 2 готовят два сопоставимых небольших пакета обращений. Два проверяющих анализируют разные пакеты вручную и через карточки; порядок меняется, чтобы снизить влияние знакомства с текстом. Записываются время, найденные темы, ошибки и время проверки карточек. Это небольшой эксперимент на синтетическом наборе, а не ретроспективная экономия компании. Если настоящие логи доступны, отдельно найти время обращения и первого продуктового решения; при отсутствии таких данных прямо указать невозможность восстановить показатель.

Финансовое приложение описывает три условных сценария эффекта на основе измеренного времени и явно заданных объёмов. Освобождённые часы отделяются от фактического сокращения расходов; эффект внедрённых улучшений не включается без подтверждённой связи с результатом. В рамках упрощённого условия кейса можно показать верхнюю границу инвестиций для простой трёхлетней окупаемости как сумму подтверждённых годовых денежных эффектов за три года. Не называть её бюджетом проекта и не выдавать отсутствие расчёта затрат за доказанную окупаемость. Макроэкономические предпосылки для финальной защиты при необходимости исследовать отдельно и снабдить источниками, не выдумывать их в пилоте.

Команда готовит ориентировочно десять слайдов: проблема и пользователь; сценарий до/после; демонстрация; компоненты и доступы; инструменты и пример промпта; данные и разные форматы; качество и приёмка; эффект и ограничения; дальнейшее развитие и промышленная архитектура; выводы и резерв демонстрации. Нумерация здесь ориентир, содержание адаптировать под регламент. Итоговый текст кейса должен отвечать вопросам 1–4 и 6 в пределах 15 000 символов, пункт 5 оформляется отдельным Markdown; это будущие материалы подачи, а не текущий ExecPlan. Добавить краткую таблицу AI Footnotes, если команда готовит это необязательное приложение.

В день 8 выполнить две полные репетиции на том компьютере, с которого будет показ. Демонстратор открывает обзор с видимым режимом, запускает обработку, показывает потребность, проверяет источник, сохраняет решение, повторяет импорт и добавляет новое обращение. Параллельно подготовить резервное видео и отдельный replay-набор. Если переключение на резерв необходимо, объявить это явно; не подменять результаты незаметно.

Проверить отсутствие внешних сетевых запросов приложения во время работы, доступность всех локальных материалов, читаемость интерфейса на экране и сохранение данных после рестарта. Сохранить идентификатор версии, настройки без секретов, сводку качества и список ограничений. ## Concrete Steps


Все команды ниже — целевой интерфейс будущего приложения. Их ещё не выполняли; разработчики должны создать указанные файлы и команды на соответствующих этапах. Примеры рассчитаны на PowerShell. Рабочая папка всегда указывается явно относительно корня нового репозитория. Если команда использует другую ОС, сохранить смысл и записать её фактический эквивалент в README.md.

В первый день из корня проекта проверить инструменты:

    py -3.12 --version
    node --version
    npm --version

Отсутствующий Python 3.12 допускается заменить доступным поддерживаемым Python после проверки зависимостей и записи решения. Не переустанавливать инструменты на чужом компьютере без необходимости. После создания backend/requirements.in установить зависимости в отдельное окружение; среди прямых зависимостей предусмотреть fastapi, uvicorn, httpx, pydantic-settings и pytest. SQLite доступна через стандартный модуль sqlite3. Все версии фиксируются после первого успешного запуска.

Из корня проекта:

    py -3.12 -m venv .venv
    .\.venv\Scripts\python.exe -m pip install -r backend/requirements.in
    .\.venv\Scripts\python.exe -m pip freeze > backend/requirements.txt
    Copy-Item -LiteralPath .env.example -Destination .env

Команду Copy-Item выполнять только при отсутствии .env; существующую конфигурацию не перезаписывать. requirements.txt создаётся из чистого окружения и затем используется остальными участниками вместо requirements.in. Актуальные версии фиксируются в первый день; этот документ не притворяется уже проверенным файлом зависимостей.

Из frontend/ после создания package.json:

    npm install
    npm run dev

Первый npm install создаёт package-lock.json, который сохраняется в репозитории. Последующие установки выполняются через npm ci. Скрипты dev, build и test в package.json должен определить участник 4; для test использовать Vitest и проверки взаимодействий, влияющих на пользовательский сценарий. Сервер разработки интерфейса открывается по адресу http://127.0.0.1:5173. Запросы /api передаются серверу на 127.0.0.1:8000.

Из backend/ при открытом отдельном терминале:

    ..\.venv\Scripts\python.exe -m app.cli init-db
    ..\.venv\Scripts\python.exe -m app.cli import --manifest ../data/demo/manifest.json
    ..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1

Ожидаемое наблюдение: /api/v1/health возвращает HTTP 200 и поля status=ok, model_mode=replay либо live, processing_state и available_models. Исправность сервера не означает доступность моделей: available_models показывает проверенное состояние отдельно. Команда import сообщает количество inserted, updated, unchanged и invalid. Вторая загрузка того же manifest должна дать inserted=0 и updated=0.

Из backend/ проверить настоящие подключения:

    ..\.venv\Scripts\python.exe -m app.cli probe-models --mode live

Эта команда отправляет короткий текст, демонстрационную запись и изображение в явно настроенные внутренние сервисы. Она не печатает токены и содержимое настоящих обращений. Успех требует корректного ответа от всех трёх адаптеров; недоступный адаптер выводится с причиной и даёт ненулевой код завершения. Этот результат не блокирует разработку replay, но блокирует утверждение о полной живой мультимодальной интеграции.

Из backend/ выполнить пакетную обработку и проверки:

    ..\.venv\Scripts\python.exe -m app.cli run --product webneft --from 2026-10-01 --to 2026-10-31
    ..\.venv\Scripts\python.exe -m pytest -q
    ..\.venv\Scripts\python.exe -m app.cli evaluate --manifest ../data/holdout/manifest.json --labels ../data/holdout/labels.json --mode live --report ../var/reports/quality-live.json

Команда run использует режим из .env и тот же pipeline, что кнопка в браузере. evaluate запускается на отдельной временной базе и не изменяет демонстрационные решения. Если внутренних моделей нет, допускается выполнить оценку с --mode replay и именем quality-replay.json, но такой отчёт проверяет воспроизведение и расчёты, а не способность модели находить неизвестные потребности. Не использовать replay в качестве замены независимой живой оценки.

Из frontend/ выполнить:

    npm run test -- --run
    npm run build

После успешной сборки перезапустить сервер, открыть http://127.0.0.1:8000 и пройти весь сценарий без отдельного сервера интерфейса. Ожидается, что источники и /api работают, а статические файлы берутся из frontend/dist/. Проверки должны завершиться без ошибок; точное число тестов записать после их появления, не объявлять его заранее.


## Validation and Acceptance


Основной синтетический набор содержит 24 уникальных обращения за октябрь 2026 года: 18 текстовых T001–T018, три аудио A001–A003, три обращения с изображениями I001–I003. Это искусственные примеры, не статистика компании. Четыре повторяющиеся темы заранее размечены: изменение телефона в оформленной заявке — T001, T002, A001, I001; машина исчезла из справочника, но повторно добавить нельзя — T003, T004, A002, I002; кнопка «Далее» не реагирует при заключении договора — T005, T006, A003, I003; явно выраженная просьба выгружать историю заказов — T007–T010. Для настройки добавить ещё 12 текстовых пограничных примеров в data/development/: отрицание проблемы; цитирование чужой жалобы; закрытый ранее случай; два разных запроса в одном тикете; почти одинаковые формулировки разных проблем; изменение исходного текста; инструкции модели внутри обращения; неясный продукт; пустой текст; просьба о звонке без описания потребности; обсуждение существующей темы; новое свидетельство по теме изменения телефона. data/development/manifest.json включает основной набор и эти 12 записей без двойного импорта. Для независимой проверки подготовить 24 новых обращения H001–H024, из них 18 текстовых, три аудио и три с изображениями. Их тексты и разметку не использовать для настройки. Предусмотреть шесть повторяющихся эталонных тем по три обращения и шесть одиночных или нерелевантных случаев. В labels.json для каждой потребности записать source_id, пользовательский сценарий, ожидаемую тему или отсутствие подходящей темы, подтверждающий фрагмент и тип. Темы, представленные минимум двумя разными обращениями в оцениваемом наборе, считаются повторяющимися. Текстовые метки для медиа сверяются человеком с исходным материалом. Разделение выполняется до запуска анализа; результаты разметки не передаются модели.

Функциональная приёмка требует, чтобы на основном наборе в replay появлялись ровно четыре повторяющиеся темы по четыре обращения и не было ложных групп из одиночных случаев. Это проверяет детерминированные сохранённые ответы и работу программы. Для live точное совпадение не предполагается заранее: проверяются те же источники и измеряются ошибки по меткам. Нельзя считать число карточек единственным критерием качества.

Целевые пороги качества пилота: точность состава групп не ниже 85% и полнота найденных повторяющихся тем не ниже 75% на независимой выборке. Точность состава — доля корректных назначений потребностей среди всех потребностей в опубликованных повторяющихся темах после сопоставления с эталонными темами; неоднородную группу нельзя зачесть целиком по красивому названию. Полнота — доля эталонных повторяющихся тем, для которых система нашла одну согласованную группу с доказательствами минимум из двух разных обращений. Сопоставление тем фиксируют два проверяющих; публикуются исходные количества и спорные случаи. Это целевые значения приёмки учебного пилота, а не доказанный уровень компании. Маленькая выборка не позволяет делать выводы о промышленной надёжности.

Для каждого фактического утверждения карточки должен существовать указанный источник; для всех чисел — воспроизводимый расчёт по базе. Эти два требования обязательны независимо от порогов модели. Доля ошибок обработки показывается отдельно для текста, аудио и изображений. Если файл не обработан, он не считается отрицательным примером отсутствия потребности. Итоговая оценка должна отдельно указать потери покрытия.

Регрессионные проверки в backend/tests/test_import_idempotence.py, test_pipeline.py, test_topic_identity.py, test_decisions.py, test_source_grounding.py и test_failures.py должны доказывать конкретное поведение: одинаковый импорт не меняет количество записей; изменение источника обновляет его потребности; новый тикет обновляет прежнюю тему; решение сохраняется после повторной обработки; ручное исключение не отменяется; бизнес-отказ не регистрируется как ошибка; придуманная цитата не публикуется; повреждённый файл и тайм-аут не уничтожают остальные результаты. Эти проверки нужны из-за сохранения решений и риска тихой ошибки данных, а не ради покрытия каждой функции.

В интерфейсе проверить действия, которые могут потерять пользовательский результат: сохранение решения с перезагрузкой, ошибка сервера без ложного подтверждения успеха, просмотр источника и недоступный материал. Одна полная ручная репетиция должна повторить маршрут от импорта до обновлённой карточки; вторая — показать отказ модели и явное переключение на резерв.

Приёмка устойчивости: повторный клик запуска возвращает текущий run_id, а не создаёт параллельную обработку. После остановки сервера незавершённый запуск становится interrupted; новый запуск повторяет только незавершённые этапы с сохранением успешных результатов. Решения, статистика и источники доступны после перезапуска. Пустой период показывает «Обращений за период нет», а не ошибку модели. Ошибки отдельных источников приводят к completed_with_errors с перечнем проблем.

Демонстрационная готовность требует работающих текста, аудио, изображения, карточки, источников, решения и повторного обновления без дублей. При отсутствии внутренних моделей может быть принят отдельный процессный прототип replay, но его нужно так и назвать; требование полной живой интеграции считается невыполненным и остаётся в Progress. Производственный доступ к БД, корпоративная авторизация и доказанная окупаемость не являются результатом хакатонного прототипа.


## Idempotence and Recovery


Источник уникален по паре product_id/source_id; версия содержимого вычисляется из текста и хешей вложений, а дата импорта не считается изменением. Точные повторы данных не превращаются в дополнительный спрос. Схожие обращения разных клиентов автоматически не удаляются. Если нет стабильного идентификатора заявителя, статистика уникальных пользователей недоступна и так и отображается.

Кэш распознавания и ответов модели учитывает содержимое, модель, версию промпта и режим live/replay. Сохранённый ответ без совпадения этих ключей использовать запрещено. При изменении промпта повторная обработка выполняется по явному запуску; карточки и решения не сбрасываются. История содержит версии и события ручного исправления.

Каждый материал обрабатывается независимо. На временную сетевую ошибку разрешены два повтора с ограниченным ожиданием; начальные тайм-ауты — 60 секунд для текста и изображения, 120 секунд для короткого аудио. Эти лимиты уточнить по результатам реальных проб. Ошибка схемы ответа допускает одну попытку уточнения формата; затем сохраняется причина. Бесконечные повторы и молчаливые заглушки запрещены. Логи содержат run_id, source_id, этап, время и тип ошибки без секретов и полного исходного текста.

Перед изменением схемы SQLite остановить обработку и штатно закрыть сервер, скопировать var/insight.db с датой в локальную резервную папку, затем применить изменение и проверить сценарий. Если используются дополнительные журнальные файлы SQLite, делать согласованную резервную копию средствами SQLite, а не копировать один активный файл. Разрушительный сброс базы не является обычным шагом запуска и не выполняется без отдельного решения команды.

Для повторной демонстрации использовать отдельную пустую базу с новым путём через APP_DB_PATH и известный набор. Старую базу и решения сохранять. Если подготовка новой базы не удалась, вернуться к прежнему пути конфигурации; не переписывать исходные материалы. Для повторного импорта неизвестный файл возвращает понятную ошибку; локальные пути вложений разрешаются только внутри каталога набора, переходы за его пределы отклоняются.

Если к концу дня 4 основные каналы не собраны, отказаться от ручного объединения и исключения групп в интерфейсе, оставив фиксацию ошибки и ручной разбор. Если к дню 6 отставание сохраняется, убрать отдельный экспорт описания задачи и график, сохранив числовую динамику. Сокращение записать во всех затронутых разделах. Не удалять доказательства, достоверные счётчики и сохранение решений ради внешнего оформления. Отсутствие модели нельзя скрывать снятием маркировки replay.


## Artifacts and Notes


Исходный manifest.json содержит объект с полями dataset_id, synthetic=true и массивом tickets. Каждый тикет содержит source_id, product_id=webneft, created_at в формате ISO 8601 с часовым поясом, текст, необязательный обезличенный requester_id и массив assets. Материал содержит asset_id, kind, относительный путь, mime_type и необязательный внутренний source_url. Период обработки интерпретируется по Europe/Moscow: включаются все обращения с начала первого дня до начала дня после to. Это исключает неоднозначность последнего дня периода.

Для воспроизведения сценария добавить data/demo/delta.json с одним новым текстовым обращением по изменению телефона и собственной уникальной записью D_PHONE_NEW. Основной импорт содержит 24 обращения, повторный — те же 24, после delta — 25. В replay тема телефона меняется с четырёх до пяти обращений; остальные три темы остаются по четыре. Идентификатор темы и решение владельца остаются прежними. Для live правильное присоединение нового обращения проверяется отдельно и не выдаётся за гарантированное свойство модели.

Ожидаемый формат наблюдений после реализации, не фактический журнал:

    import #1: inserted=24, updated=0, unchanged=0, invalid=0
    import #2: inserted=0, updated=0, unchanged=24, invalid=0
    run: mode=replay, state=completed, tickets=24, recurring_topics=4
    delta: inserted=1, phone_topic_count=5, same_topic_id=true, decision_preserved=true

В var/reports/ сохранить результаты проверок, quality-live.json либо честно названный quality-replay.json и текстовую сводку. В README.md записать версию проекта, проверенные инструменты, время демонстрационного прогона, известные ограничения и маршрут запуска. В записи демонстрации должно быть видно обозначение synthetic и режим обработки. Ни один ожидаемый фрагмент этого плана не переносить в презентацию как уже полученный результат.


## Interfaces and Dependencies


Общие структуры определяются в backend/app/schemas.py до параллельной реализации. TicketInput содержит source_id, product_id, created_at, text, requester_id и assets. NormalizedDocument содержит source_id, content_hash, version и fragments; каждый Fragment содержит fragment_id, asset_id либо null для текста, kind, text, необязательные start_ms/end_ms и warning. ExtractedNeed содержит need_id, source_id, fragment_id, evidence_quote, scenario, need_type, statement, explicit_request, improvement_hypothesis и uncertainty_reason. Topic содержит постоянный topic_id, product_id, title, scenario, summary, need_ids, evidence, status, owner и version. TopicStats содержит ticket_count, requester_count либо null, weekly_counts, first_seen и last_seen. Run содержит run_id, mode, state, этап, число успешных/ошибочных материалов и timestamps. DecisionEvent и AnalysisFeedback хранятся отдельно.

В gateways.py определить порты — внутренние интерфейсы, по которым приложение вызывает заменяемые адаптеры. TextGateway принимает нормализованные фрагменты и промпт с ожидаемой схемой, возвращает проверенный результат и метаданные вызова. AsrGateway принимает разрешённый локальный аудиоматериал и возвращает текст с необязательными временными метками. VisionGateway принимает изображение и возвращает связанные с обращением фрагменты. Replay-адаптеры реализуют те же интерфейсы и ищут записи по хешу запроса, идентификатору модели и версии промпта; неизвестный вход возвращает REPLAY_RECORD_MISSING. Для новых входов live никогда не используется ответ от похожего сохранённого примера.

Сигнатуры инструментов внутри приложения зафиксировать как import_tickets(manifest), normalize_ticket(ticket), transcribe_audio(asset), describe_image(asset), extract_needs(document), assign_topic(need, candidate_topics), calculate_topic_stats(topic_id, period), build_evidence_card(topic_id), get_source(source_id), record_decision(topic_id, decision), record_feedback(topic_id, feedback), merge_topics(source_topic_id, target_topic_id), exclude_needs(topic_id, need_ids), build_report(product_id, period). Импорт и нормализация принадлежат участнику 1; извлечение, назначение и текст карточки — участнику 2; сохранение, статистика, решения и отчёт — участнику 3. Модель не вызывает произвольные функции: pipeline.py управляет порядком и проверяет результат.

Минимальный HTTP-контракт начинается с /api/v1. GET /health возвращает исправность приложения и явно отдельный статус моделей. POST /runs принимает product_id, date_from и date_to, возвращает 202 с run_id; режим берётся из серверной конфигурации и виден в ответе. GET /runs/{run_id} возвращает прогресс. GET /topics принимает продукт, период и статус; по умолчанию показывает повторяющиеся темы минимум с двумя различными source_id. Одиночные потребности доступны отдельным фильтром и не теряются. GET /topics/{topic_id} возвращает карточку, статистику, источники и историю решения.

PATCH /topics/{topic_id}/decision принимает status, owner, reason и необязательные existing_issue_url и review_after. Для linked ссылка обязательна; для deferred нужна дата пересмотра; для declined нужна причина. POST /topics/{topic_id}/feedback принимает kind и comment. POST /topics/{topic_id}/merge принимает target_topic_id; запрещается объединение разных продуктов. POST /topics/{topic_id}/exclude принимает need_ids, существующие в этой теме. GET /sources/{source_id} возвращает разрешённый текст и ссылки на материалы, GET /assets/{asset_id} отдаёт разрешённый демонстрационный файл; браузеру не выдаётся произвольный файловый путь. GET /reports принимает продукт и период и отдаёт Markdown. Веб-загрузка произвольных файлов не входит в MVP: импорт выполняется командой из известного каталога, пользователь в браузере запускает анализ уже зарегистрированных материалов.

Все ошибки HTTP имеют поля code, message и необязательный run_id. Пользователь видит объяснение, а не трассировку программы. Неизвестная тема даёт 404, неподходящие данные — 422, недоступный материал — понятный статус с причиной. Во время активного запуска повторный запрос возвращает его идентификатор; не допускаются два параллельных изменения одной демонстрационной базы. Даты, уникальные идентификаторы, ручные исправления и числовая статистика проверяются сервером, а не доверяются тексту модели.

В .env.example определить APP_MODEL_MODE=replay, APP_DB_PATH=var/insight.db, APP_DATA_ROOT=data, TEXT_MODEL_BASE_URL, TEXT_MODEL_ID, TEXT_MODEL_TOKEN, ASR_BASE_URL, ASR_MODEL_ID, ASR_TOKEN, VL_BASE_URL, VL_MODEL_ID, VL_TOKEN. Пути разрешаются относительно корня проекта независимо от папки запуска. Секреты пустые. Фактические методы и адреса транспорта заполняются по результатам первого дня. В live отсутствующая конфигурация даёт MODEL_NOT_CONFIGURED; в replay она не нужна. Приложение не устанавливает соединений с публичными моделями, сервисами аналитики и внешними шрифтами.

FastAPI обрабатывает HTTP, httpx выполняет ограниченные по времени вызовы внутренних моделей, Pydantic проверяет структуру, sqlite3 хранит данные. ThreadPoolExecutor с одним рабочим потоком запускает последовательный pipeline без блокировки чтения карточек; у потока свои соединения с базой и короткие операции записи. Один процесс uvicorn обязателен в пилоте. React показывает интерфейс, Vite собирает локальные файлы, Vitest проверяет критические действия интерфейса, pytest — сохранение данных и обработку ошибок. Не добавлять Redis, Celery, Kubernetes, отдельную векторную БД или новую модель без зафиксированной потребности.

Проверенные при составлении первичные ориентиры: [документация Vite](https://vite.dev/guide/) описывает требования Node.js; [документация SQLite](https://www.sqlite.org/whentouse.html) указывает ограничение одного одновременного писателя; [документация FastAPI](https://fastapi.tiangolo.com/tutorial/background-tasks/) отличает небольшую фоновую работу от задач, требующих отдельных средств выполнения. Эти сведения поддерживают ограничение пилота, но не заменяют измерение нагрузки. Весь необходимый для выполнения выбор включён в план; читать внешние страницы для понимания сценария не требуется.
