## Purpose / Big Picture

GPN Insight анализирует обращения, выделяет потребности, категории и объяснимые приоритеты, группирует повторы и формирует сводку для руководителя поддержки и продуктовой команды. Поддержка продолжает обычную работу без обязательной ручной разметки и эскалации неясных случаев. Агент не отвечает клиентам и не устраняет неполадки; решение о продуктовых изменениях остаётся человеку.

Основной бизнес-фокус задания — повторяющиеся некритичные пожелания, которые теряются при передаче в продукт. По вебинару выявление пропущенных серьёзных случаев — дополнительная ценность аналитики, а не замена этого фокуса полноценным incident management.

По решению пользователя 09.11 ближайшие 2–3 полных дня посвящены прототипу, включая медиа, насколько успеем. Итоговые документы команда создаёт вместе в последние дни. Основной получатель отчёта — предположительно руководитель поддержки, период — неделя; продуктовые темы передаются продуктовой команде. Получатель уточняется командой, еженедельный ритм принят пользователем. Локальная кнопка формирования недельного отчёта не означает работающую доставку по расписанию.

Последующее согласование 09.11: приняты предложенные пять категорий/четыре приоритета; при ошибке вложения анализируются успешные части; недельный отчёт охватывает последнюю завершённую календарную неделю, понедельник–воскресенье Europe/Moscow. Руководитель должен видеть результаты прошлой недели в понедельник. Реализацию расписания/доставки не подразумевать уже готовой. Порядок конкретных задач и копируемые запросы — `docs/NEXT_IMPLEMENTATION_TASKS.md`.

Основания: `docs/task.pdf` (7 страниц) и предоставленная выжимка `docs/org_feedback.txt` (вводная/ответы 1–21). Дата вебинара неизвестна, выжимка не является заверенной стенограммой. ## Surprises & Discoveries

09.11.2026, итоговая приёмка: новый разнообразный демонабор действительно даёт одну повторяющуюся тему по двум source_id, три темы при support_level=all и один неясный review. Ранее пустой default список объяснялся одним источником, а не отсутствием интеграции. Authored ответы строятся только отдельной подготовкой; штатный backend использует ReplayGateway. ASR/VL injection cases проверяют недоверенный текст, не устойчивость живой модели в звуке/пикселях.

2026-11-09, A4–A7: хранить только текущие fragments нельзя — прежние passport/override evidence требуют исторических записей. Revision publication добавляет immutable history и деактивирует needs/links без удаления. Снятие active связи увеличивает topic.version и выставляет visible manual recheck; status/owner/паспорт/DecisionEvent не переписываются. Контрольный rollback после изменения links/overrides откатил всё. Replay подтверждает лишь точные известные requests: пользовательская правка каталога может законно потребовать новый authored record.

2026-11-09, A1–A3: MergePreview тоже содержит два TopicDetail со вложенными sources. Одна защита GET source/card не закрывала этот путь: regression на synthetic nonsynthetic-marked записи упала с raw sentinel до подключения public projector к merge-preview и прошла после. DTO semantic revision не заменяет SQL revision publication: отдельный Normalizer намеренно не пишет legacy documents/needs.

2026-11-09: работа У4 уже слита в GitHub main, поэтому не требуется перенос файлов/второй клон: frontend-only fast-forward сохраняет наши незакоммиченные документы. Важный риск partial: нынешний immutable document/needs и source/profile extraction key нельзя повторно использовать как полный результат после позднего успеха ещё одного asset. До включения partial нужны revision/digest успешных fragments, независимые material checkpoints и сохранение прежних business decisions. Просто удалить document.errors недостаточно.

Ответы 4/12: прототип добровольный, доступа к моделям не будет. Ранее план зависел от недоступных live ASR/VL. Теперь live — граница целевого внедрения, а не причина срыва демонстрации. Допустимость synthetic данных подтверждена; authored replay — наш честно маркированный способ показать программу, а не подтверждение качества моделей.

В `backend/app/schemas.py` нет отдельного бизнес-контракта category/priority/criticality; `need_type` и `Topic.status` не заменяют их. `backend/app/report.py` выводит темы/счётчики/решения/review/errors, но пока не содержит требуемую категориально-приоритетную сводку. Ответ 21 и заключение вебинара выявляют реальный пробел, а не косметическую правку.

Текущие product_id/source_id/source_content_hash обеспечивают идемпотентность и версии. Два разных source_id (текст и звонок) по одному инциденту пока считаются двумя источниками. Пять минут из ответа 13 — пример стратегии, не правило автоматического объединения. Статусы тикетов из ответа 18 не являются статусами наших тем.

Task.pdf, стр. 5: основной документ — doc/docx/pdf до 15 000 символов, ответы 1–4 и 6; пункт 5 о метриках — отдельный .md; презентация примерно 10 слайдов. Выжимка называет .md с промптом. Готовить рабочие материалы обоих типов, уточнить конечный комплект; не использовать приложения/ссылки для обхода лимита. ## Architecture and Product Boundaries

Пилот: локальный браузер → общий preview/commit → нормализация/маскирование → категории/приоритеты/потребности и сопоставление → программные счётчики/доказательства → недельный отчёт/добровольное решение. Целевое внедрение: единая система/телефония → инкрементальный коннектор с контрольной точкой → подготовка материалов с ASR/VL → аналитика → сводка руководителю поддержки и продуктовой команде. Существующие корпоративные системы можно принять допущением по бизнес-процессу; собственные monitoring/jobs/access/storage компоненты нужно описать. Task.pdf оценивает обоснование сервисных границ и нагрузки. Одна FastAPI/SQLite-сборка подходит пилоту; целевую диаграмму разбить на ingestion, material processing, analytics, reporting/access и monitoring/state с объяснением ответственности. Это логические сервисы, не обещание внедрённых контейнеров/брокера. Для потока V_day=400–480 по всему контуру задать активные часы h, peak factor b, доли форматов и длины записей как неизвестные/допущения. λ_avg=V_day/(h×3600), λ_peak=b×λ_avg. Число ASR/VL — число материалов, текстовых вызовов — сумма extract/assign batches/propose и новых операций, а не одно обращение=один вызов.
