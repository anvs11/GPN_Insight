# Безопасно импортировать медиа и восстанавливать файлы после прерывания

Серверный срез реализован в feat/u1-media-import по прямому поручению пользователя; здесь зафиксированы спецификация, фактические результаты и оставшаяся внешняя приёмка. ## Purpose / Big Picture


После выполнения аналитик сможет отправить подготовленный JSON вместе с WAV/MP3 и PNG/JPEG, увидеть предварительные счётчики, подтвердить импорт и повторить тот же набор без дублей. При обрыве загрузки, остановке процесса или потере ответа сервис сохранит зарегистрированные файлы, обнаружит незавершённые операции и не удалит исторические материалы. CLI применяет те же правила к файлам набора.

Этап заканчивается проверенным хранением медиа и восстановлением, не распознаванием. Qwen-ASR/Qwen-VL, медийные checkpoints/replay, выдача бинарных источников в браузер и снятие ограничений Normalizer/Pipeline выполняются следующими согласованными задачами. Текстовые preview/commit, masking, HTTP/CLI и SQLite v3 уже существуют и переиспользуются. Один продукт webneft, один серверный процесс; брокер, новая БД, архивы, видео и внешние сервисы не добавляются.

## Surprises & Discoveries

Сверка U2/U4 07.11.2026: shared DTO уже позволяют описать media-source/provenance, но не содержат duration/размеров изображения и не задают persistent ApprovedAsset resolver или media replay. Расширять их ради документа не требуется. Текстовый API уже в main; наличие локальных media-файлов не означает публикацию.


2026-11-07, ревью: Pydantic/JSON ошибки локального реестра и owner не были RepositoryError и обходили HTTP503-контракт; после исправления безопасный код возвращается без input/traceback, материалы/БД сохраняются. На CPython 3.13 глубина 2500 JSON ещё разбирается, а 25000 уже даёт RecursionError при размере меньше 64 КиБ — теперь он преобразуется в ошибку журнала. DTO RegisteredMaterial не содержит product_id, поэтому поиск reuse через полный список ошибочно проверял чужой продукт; для reuse берётся product-specific view существующего метода, а общий registry preflight/cleanup по-прежнему полный.

2026-11-07, реализация: одного server UUID в planned-пути недостаточно, чтобы удалять final-файл при коллизии уже существующего каталога. Журнал теперь фиксирует dev/inode после эксклюзивного mkdir до первого transfer; несовпадение сохраняет каталог для проверки. EXCL hard-link transfer оставляет при kill между link/unlink две собственные ссылки; recovery узнаёт их по inode и безопасно завершает перенос. До SQL дополнительно проверяется fingerprint staged-файла и SHA-256 final-файла, чтобы ожидание guard не публиковало изменённые байты. Эти случаи покрыты отдельными регрессиями и process-stop.

2026-11-07, совместимость: Pillow 13.0.0 имеет CPython 3.13 ARM64 wheel; mutagen 1.48.1 установлен как pure-Python wheel. Все прежние 25 pins совпали, обновлений не было. На текущем Python 3.13.0/macOS ARM64 прошли 646 tests, включая 59 новых поведенческих cases, один прежний Starlette/AnyIO warning. Read-only CLI не восстанавливает hot SQLite journal записью: перед файловой recovery после такого прерывания нужен штатный startup/init-db существующей БД. Корни и журнал при неопределённости сохраняются.

MaterialInput.path проверяет лишь простое имя без `/`, `\`, `:` и не запрещает все опасные Windows/Unicode-имена. RegisteredMaterial проверяет синтаксис относительного storage_path, не наличие и не содержимое файла. DatasetRegistration требует точное соответствие всех assets и materials уже при создании объекта. Поэтому нельзя просто убрать MEDIA_NOT_SUPPORTED и валидировать исходную оболочку как готовый DatasetRegistration: сначала нужны TicketInput и проверенные метаданные файлов. Общие DTO при этом не требуется дублировать.

Repository.register_dataset сам повторно входит в import_commit. Текущий OperationGate реентерабелен для того же thread ID, поэтому внешний guard вокруг файлового размещения совместим с существующей регистрацией. Guard привязан к разрешённому пути SQLite и существует только в памяти процесса: это не межпроцессная блокировка CLI/сервера.

source_content_hash исключает server storage_path и original asset.path, но учитывает asset_id, kind, MIME, source_url и хеш байтов. При unchanged регистрация пропускает цикл материалов; при повторном asset_id/hash может оставить прежний storage_path. request_hash регистрации, напротив, вычисляется по полному DatasetRegistration, включая предложенные пути. Поэтому новый HTTP-запрос получает новый UUID; повтор того же UUID допустим только с тем же точным подготовленным batch, а не с заново придуманными путями.

registered_materials(product_id=None) возвращает все записи реестра, включая материалы старых source_versions. Он не обращается к файловой системе. get_source и source_materials читают метаданные, но не проверяют целостность байтов. В main.lifespan сейчас есть initialize и interrupt_active_runs, файловой сверки нет. RunService создаёт executor в конструкторе, но до POST /runs задания не отправляются; сверка должна закончиться до yield lifespan.

HTTP сейчас сначала накапливает весь body в bytearray: максимум 1 114 112 байт; manifest/часть — 1 048 576; части/поля/файлы — по 8; заголовки части — 8 192; boundary — 70 ASCII-байт; parser.write — порциями 32 768. files отклоняются целиком. В закреплённом python-multipart проверка on_end уже обязательна, одного finalize недостаточно. Увеличить только MAX_BODY_BYTES до 52 МБ недостаточно для безопасного медиа-пути.

В importer есть два отказа: assets-параметр и assets внутри manifest. TextNormalizer отвергает весь ticket с MEDIA_NORMALIZATION_NOT_SUPPORTED; Pipeline до нормализации выставляет MEDIA_PIPELINE_NOT_IMPLEMENTED и считает ошибки материалов. API GET /assets отсутствует; SourceViewer явно сообщает, что просмотр файлов недоступен. Эти ограничения нельзя объявить снятыми успешным импортом.

Baseline предыдущей задачи: Python 3.13.0/macOS ARM64, 587 passed с одним известным Starlette/AnyIO warning, реальные HTTP/CLI/restart прошли на синтетике. Старый check_text_normalizer отдельно падает на v1-профиле handoff вместо текущей v3 и другом proposal hash; этот план не исправляет и не скрывает тот отказ. Подробности — var/reviews/u1-baseline-20261107/BASELINE.md. Новые проверки данного этапа ещё не выполнялись.

## Context and Orientation


Источник — TicketInput со стабильными source_id/product_id, created_at, текстом, requester_id и списком MaterialInput. Материал — ровно один файл с уникальным asset_id. Manifest — UTF-8 JSON с ровно dataset_id, synthetic, tickets; product_id источников только webneft. В manifest нет server storage_path, origin, registration_id, абсолютных путей или модели. source_url — сохранённые данные, никогда не адрес для скачивания.

RegisteredMaterial содержит asset_id, kind, SHA-256 байтов, относительный storage_path, original_filename, проверенный MIME и положительный byte_size. В нём нет duration, width/height, признака распознавания или asset URL. DatasetRegistration связывает tickets и materials один-к-одному; shared schemas принадлежат U3. ImportPreview/ImportResult считают обращения inserted/updated/unchanged, не файлы. Не добавлять число вложений в эти счётчики и не выдавать наличие файла за успешную обработку.

backend/app/ingestion/importer.py реализует общий import_tickets; imports_api.py — multipart-оболочку; cli.py — чтение manifest и вызов того же сервиса. backend/app/storage.py содержит preview_dataset_counts, register_dataset, import_commit и registered_materials; Repository наследует их. coordination.py — текущий process-local guard, db.py — транзакции. Прежний importer запрещает внешний repository._db, поскольку не может подтвердить чужой commit; запрет сохранить.

Новые небольшие модули: backend/app/security.py для проверки имён, путей, форматов и лимитов; backend/app/ingestion/media_files.py для владения временными файлами, журналирования размещения, сверки и восстановления. Не переносить сюда SQL, группировку, вызовы моделей или логику решений. Новые тесты — test_upload_security.py, test_media_import.py, test_import_recovery.py; расширить существующие test_imports_api.py/test_import_cli.py, не дублируя их целиком.

Пути Settings разрешаются от корня репозитория: APP_UPLOAD_ROOT=var/uploads, APP_TMP_ROOT=var/tmp. У одной БД должна быть собственная пара корней. Отдельные проверочные БД всегда получают отдельные uploads/tmp в своём UUID-каталоге; нельзя использовать общий var/uploads с несколькими независимыми тестовыми БД.


## Interfaces and Dependencies


Ниже внутренние Python-интерфейсы реализованного среза, не новые shared DTO или HTTP-контракт. Они выполнены по прямому поручению пользователя; независимый review U3 остаётся в передаче. import_tickets сохраняет прежние позиционные аргументы и добавляет только серверный keyword workspace; текстовые вызовы с assets=() не требуют workspace:

    import_tickets(manifest: bytes | str,
                   assets: Collection[StagedUpload] = (),
                   dry_run: bool = False, *,
                   repository: Repository | None = None,
                   registration_id: str | None = None,
                   workspace: ImportWorkspace | None = None
                   ) -> ImportPreview | ImportResult

В media_files.py определить внутренние dataclass StagedUpload(original_filename: str, temporary_path: Path) и ImportWorkspace. Серверный context manager open_import_workspace(settings: Settings, repository: Repository, *, dry_run: bool) -> ContextManager[ImportWorkspace] создаёт request UUID, доверенные канонические roots, временный журнал и каталог запроса с ограниченным доступом. Он не создаёт owner-маркеры или uploads-каталоги в preview: постоянная инициализация принадлежности выполняется только отдельно при startup либо под commit-guard. ImportWorkspace.stage_stream(original_filename: str, stream: BinaryIO) -> StagedUpload ограниченно копирует CLI-поток; HTTP callback использует тот же примитив записи порций/счёта, не повторяя правила. Принимаются только обычные серверные staged-файлы внутри данного workspace, без symlink/подмены; dataclass из клиентского JSON не создаётся. Поля устройства/inode/реально измеренного размера могут быть частными деталями, не новыми общими схемами. При нормальном выходе context manager убирает собственные временные файлы; при неопределённом commit сохраняет журнал и спорные final-файлы для сверки, не выполняет безусловный rmtree.

В security.py определить validate_upload(upload: StagedUpload, material: MaterialInput, workspace: ImportWorkspace) -> RegisteredMaterial. Функция проверяет весь файл, вычисляет хеш, выбирает серверный будущий storage_path и возвращает существующий DTO; сама не сохраняет запись SQLite. MIME берётся из подтверждённого формата и должен точно совпасть с manifest. Ни transport Content-Type, ни расширение по отдельности не служат доказательством формата.

Для media_files.py определить finalize_import_files(workspace, batch: DatasetRegistration, repository: Repository, registration_id: str) -> ImportResult и reconcile_import_storage(repository: Repository, settings: Settings, *, read_only: bool = False) -> RecoveryReport. Finalize — часть вызова import_tickets, не альтернативный импорт: использует существующий import_commit/register_dataset. RecoveryReport — внутренний dataclass с outcome=ok|issues, кодами проблем, asset_id при наличии и счётчиками сохранённых/убранных остатков; не добавлять его в schemas.py без отдельного согласования. В read_only=True сверка не создаёт маркеры/постоянный отчёт и ничего не удаляет; результат возвращается в памяти. Журнал и обычный отчёт не содержат тексты, клиентские контакты или секреты.

Новые runtime-библиотеки — Pillow==13.0.0 для PNG/JPEG и mutagen==1.48.1 для MP3, зафиксированы в requirements.in/requirements.txt по разрешению пользователя выбрать/проверить pins. Python 3.13.0/macOS ARM64 проверен, Windows runtime пока нет. Существующие пакеты не обновлялись, ffmpeg/внешний сервис не добавлялись. Импорт и проверка не обращаются к ASR/VL; совместимость их API не предполагается. Историческое ограничение выбора pins на стадии планирования снято указанным новым поручением.


## Limits and File Validation


Согласовать следующие точные пределы: 100 tickets; manifest 1 048 576 байт; JSON depth 32; 30 media files; сумма байтов медиа 52 428 800 (50 МиБ); фактическое HTTP-тело 54 525 952 (52 МиБ). WAV/MP3: каждый не более 10 485 760 байт и 60 секунд. PNG/JPEG: каждый не более 5 242 880 байт и 25 000 000 пикселей. Пустые файлы отклоняются. Положительные существующие APP_MAX_AUDIO_SECONDS/APP_MAX_IMAGE_PIXELS допускают согласованное уменьшение этих пределов; значения сверх границ пилота или неположительные дают явную ошибку конфигурации, не скрыто расширяют объём.

Multipart: ровно один manifest, не более 30 files, максимум 31 часть/31 file-part с учётом manifest-file, максимум одно обычное поле manifest. Manifest может быть file-part или обычным полем, как сейчас. Лимит заголовков каждой части 8 192 байта, boundary 1–70 печатных ASCII-байт без конечного пробела; чтение/передача parser.write порциями не более 32 768. На стадии приёма одна неизвестная media-part ограничивается 10 МиБ, после определения формата применяется также более строгий image cap. Финальный on_end обязателен. Повторные поля/заголовки, неизвестные поля, вложенный multipart, compressed content-encoding и незавершённый конверт отклоняются целиком.

Имена в manifest и uploads должны быть простыми, NFC и точно совпадать по исходному написанию. Не нормализовать имя молча: сравнение NFC.casefold используется для выявления коллизий, но не для выбора другого файла. Запретить `/`, `\`, `:`, NUL/управляющие символы, `.`/`..`, начальную точку, конечные пробел/точку, Windows reserved basenames (CON, PRN, AUX, NUL, COM/LPT с зарезервированными цифрами, включая системно значимые варианты), неоднозначные Unicode/casefold-дубли. Размер имени ограничить и 255 символами схемы, и 255 байт UTF-8. Разрешённые расширения без учёта регистра: .wav/.mp3/.png/.jpg/.jpeg. Уникальность имён — во всём наборе, ID материалов — прежняя проверка во всём наборе. Один файл не используется двумя assets; дубликат байтов с разными корректными asset_id сам по себе не запрещён.

CLI читает только перечисленные в manifest простые имена внутри разрешённого каталога manifest. Неперечисленные соседние файлы каталога не считаются переданными вложениями и не сканируются рекурсивно. HTTP передаёт явную коллекцию files: лишний или недостающий файл — ошибка всего набора. Проверять конечный путь, обычный тип файла и отсутствие symlink/reparse point; контролировать inode/device до и после чтения, где платформа позволяет, и не считать один resolve защитой от подмены. Для Linux/macOS использовать no-follow/dir-relative операции, для Windows — проверенный эквивалент; неподдержанную защиту не объявлять реализованной. Выбранная политика CLI отклоняет также небезопасные hardlink-источники, не давая чтению выйти за разрешённый набор через заранее созданную ссылку.

Для WAV использовать wave с чтением заявленных кадров и проверкой контейнера, положительных параметров, непротиворечивого числа кадров/длительности и отсутствия усечения; поддерживаемые варианты WAV подтвердить на синтетических примерах, неизвестный subtype отклонить явно. Для MP3 использовать mutagen.mp3.MP3, проверяя успешный разбор, конечную положительную длительность ≤60 и параметры потока, а также повреждённые/усечённые регрессионные примеры. Это не обещание полного декодирования любой порчи MP3: нераспознавание ASR позже остаётся отдельной видимой ошибкой. Для PNG/JPEG использовать Pillow, проверять распознанный формат, положительные dimensions, width×height, verify и повторное открытие/load в пределах пиксельного бюджета. Ошибки/decompression-bomb warnings считать отказом; неподдержанные многостраничные/анимированные варианты явно отклонять в согласованных пределах пилота. Не перекодировать файлы, не выполнять EXIF-инструкции и не обращаться к ссылкам/путям из содержимого. Метаданные duration/dimensions нужны для проверки, но не добавляются в RegisteredMaterial без необходимости.

### Milestone 3 — разместить файлы и подтвердить SQLite


ImportWorkspace имеет серверный request UUID и каталог APP_TMP_ROOT/imports/<request_uuid>; final-пути — APP_UPLOAD_ROOT/requests/<request_uuid>/<file_uuid>.<подтверждённое расширение>. Имена клиента, dataset_id, source_id/asset_id не образуют пути хранения. Tmp и uploads должны иметь одинаковый st_dev; перенос между дисками запрещён как конфигурационная ошибка. Использовать собственные новые каталоги с исключительным созданием, не перезаписывать существующие файлы/каталоги и не применять os.replace к final-файлам.

До перемещений записать ограниченный journal.json с schema version, request UUID, идентичностью БД/roots, фазой и полным списком будущих серверных путей/хешей/размеров. Журнал не хранит обращения или готовую авторскую разметку; это не recording. Обновлять его через атомарную смену собственного journal-temp, с flush/fsync файлов и каталогов там, где платформа поддерживает. Обещание этапа — восстановление после остановки процесса; устойчивость к аппаратному сбою/отказу диска не заявлять без отдельной проверки.

Вся проверка байтов проходит до короткой DB-транзакции. Затем в одном синхронном thread выполнить with repository.import_commit(): перечитать полный реестр, проверить целостность используемых уже зарегистрированных материалов, зафиксировать planned-пути в журнале, переместить новые staged-файлы в эксклюзивно созданный final-каталог и вызвать repository.register_dataset(batch, registration_id=request_uuid). Внешний guard удерживается до послерегистрационной сверки. Реентерабельный внутренний guard register_dataset сохраняется; внешнюю repo.transaction не открывать. HTTP await не разрывает эту критическую секцию; всё передаётся одним вызовом run_in_threadpool. Отмена запроса после передачи в threadpool не запускает cleanup параллельно работающему finalize: сначала закончить или дождаться его результата и реестровой сверки; потерянный ответ допускается, удаление зарегистрированных файлов — нет.

Успех возвращать только после успешного возврата register_dataset с законченным DB commit. Затем перечитать repository.registered_materials() без product/current-фильтра, удалить только final-файлы текущего workspace, отсутствующие в полном реестре, и убрать завершённый temp-журнал. При exception/неопределённом результате commit сначала сделать ту же авторитетную сверку, а не доверять локальному boolean «commit ещё не дошёл». Если реестр недоступен или найден подозрительный путь, ничего спорного не удалять, оставить журнал и вернуть безопасную ошибку состояния. После подтверждённого commit сбой очистки/ответа не откатывает SQLite и не разрешает удалять зарегистрированный файл; точный повтор данных с новым UUID безопасен.

Preview использует будущие UUID-пути только в памяти; они не входят в source_content_hash и не обещаются клиенту. Между preview и commit — новый запрос с полной перепроверкой, новым workspace и новым request UUID. Если библиотечный вызывающий код применяет прежний registration_id, batch обязан быть побайтово тем же по семантике сериализации, включая storage_path; автоматического восстановления «того же UUID с новыми путями» не делать.

Готовность: первый набор inserted, точный новый запрос unchanged; новое содержимое одного media создаёт ровно новую версию источника и сохраняет прежний зарегистрированный файл. Решение/история/topic ID не теряются; requires_recheck у ручных исправлений ведёт существующее хранение. Повторные одинаковые байты не заставляют систему удалять старый канонический путь или публиковать новый лишний файл.


### Milestone 4 — сверка после остановки и повреждения


Каждая пара roots принадлежит ровно одной канонической SQLite. Используется небольшой owner-маркер в uploads и owner в журнале tmp с версией формата и SHA-256 канонического пути БД, без секретов. Создавать его автоматически только для новых пустых корней. Непустой legacy-корень без подтверждённого владельца, другое значение маркера или перенос БД — причина остановить автоматическую очистку и запросить отдельную проверку привязки, сохранив данные. Это предотвращает очистку материалов другой проверочной БД. Реализация выполнена по прямому поручению пользователя; review U3 остаётся внешней приёмкой. Универсальный мигратор и автоматическое «усыновление» чужих uploads не добавляются.

После initialize и interrupt_active_runs, но до yield lifespan, U3 вызывает reconcile_import_storage. Реестр читается полностью для всех продуктов и исторических версий. Сначала проверить доступность корней/owner-маркеров/реестра, затем существование, обычный тип, размер и SHA-256 каждого зарегистрированного материала; не считать невидимый/повреждённый файл бесхозным и не чинить его молча. Неразрешимый путь/symlink либо отказ чтения реестра запрещает удаляющую фазу. Обычная отсутствующая/повреждённая зарегистрированная запись сохраняется и отражается как проблема целостности; остальные доказанно безопасные операции не должны её скрывать.

Восстанавливать незавершённые managed-запросы только по валидному серверному UUID-каталогу и ограниченному журналу. Проверять каждую запись журнала относительно её request namespace и roots, не выполнять пути из JSON буквально. Даже фаза prepared не разрешает удаление без сверки с полным реестром: процесс мог погибнуть после commit до обновления журнала. Зарегистрированные final-файлы сохранить, незарегистрированные собственные planned-файлы удалить, staged/raw-файлы завершённого/прерванного запроса закрыть и убрать. Неизвестные файлы вне managed namespace, битый/отсутствующий journal с неоднозначными final-файлами или чужая запись сохраняются для ручной проверки, не подвергаются рекурсивному удалению. Не использовать возраст файла как доказательство отсутствия владельца.

RecoveryReport сохраняется в var/reports/import-recovery-<server_uuid>.json с безопасными кодами/ID и итогом; нет текстов/контактов/traceback в пользовательском ответе. Выполнено подключение к health существующего integration_errors для кодов IMPORT_STORAGE_UNAVAILABLE/REGISTERED_MATERIAL_INTEGRITY_FAILED и к media-import ответ 503 при непригодном storage. Это выполненное аддитивное подключение без новых полей shared DTO; независимый review U3 указан в передаче. Не сбрасывать pipeline_ready текстовой сборки только из-за media-интеграции. U4 показывает код/действие, а не «потребностей нет». Текстовый путь с исправной БД не блокировать только из-за одного повреждённого media; будущая обработка такого материала остаётся отдельной ошибкой.

CLI media выполняет согласованную сверку перед своей операцией при остановленном сервере и других CLI: для --dry-run только read_only=True, без очистки/постоянной инициализации, для commit — полную. Перенос или замена SQLite из backup при прежних roots требует отдельной сверки принадлежности/истории до разрешения удаляющей recovery; одного совпадения строки пути БД недостаточно для утверждения о безопасности такой операторской операции. Нельзя объявить конкурентные отдельные процессы безопасными по одному лишь process-local guard. Дополнительный lock service не реализуется в этом объёме; если команда требует такую конкуренцию, это отдельное решение и пересмотр приёмки до кода.

Готовность: настоящий дочерний процесс останавливается после staging, после первого final-move до commit, внутри DB-транзакции с rollback и после commit до ответа; новый процесс делает сверку и повтор безопасен. Старые registered файлы и история доступны, новая частичная активная запись не появляется, повреждение зарегистрированного файла видно, отказ чтения БД не приводит к удалениям.

## Idempotence and Recovery


Повтор пользователя — новый workspace/UUID с теми же байтами; источник unchanged, даже если новые prepared-пути отличаются. Изменение байтов — штатное версионирование repository, не перепись истории. Все cleanup выполняются только над доказанно принадлежащими запросу unmanaged-файлами после полного чтения registered_materials; неизвестность означает сохранить, сообщить и повторить сверку после устранения причины. Не запускать «очистку var», reset базы или удаление historical media для достижения зелёного теста.

После неудачного импорта оператор повторяет тот же набор после устранения указанной причины. При потерянном ответе новый запрос может дать unchanged — это нормальное подтверждение уже совершившегося commit. После сбоя очистки оставшийся журнал даёт безопасную стартовую сверку; пользовательский результат не откатывается. Изменённый владелец roots/нечитаемый реестр требует проверки конфигурации, а не принудительной перезаписи owner marker.
